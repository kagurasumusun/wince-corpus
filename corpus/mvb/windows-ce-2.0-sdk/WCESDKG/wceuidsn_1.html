Designing Windows and Dialog Boxes

Many graphical user interfaces use the "desktop metaphor,". which simplifies common file operations by presenting them in the language of the paper-based world. Depicting paper documents as files, folders as directories, and a trash can for deletion are examples of the desktop metaphor. Though appropriate for most applications running on an H/PC or similar device, this metaphor may not be appropriate for some embedded systems such as a car navigation application or point-of-sale device. If the desktop metaphor is not appropriate for your application, use a "real-world" metaphor that seems suitable, since a good metaphor provides familiarity with the application which increases usability. One metaphor commonly used in virtual reality applications is the "room" metaphor.

If the desktop metaphor is appropriate for your application, present objects in windows and dialog boxes to provide a context for your application. Because some Windows CE-based devices have limited screen space, windows should generally occupy the full-screen, unless your application is used in conjunction with another application. Windows CE Help and the Calculator are examples of applications whose windows do not take up the full screen because the user benefits from seeing another window behind them. If you are creating this type of application, design your window to be a fixed size, because Windows CE does not support user resizing of windows.

An important factor to be aware of when designing overlapping windows for Windows CE is that users navigate from one open window to another by tapping the window's button on the taskbar. Users restore a window by tapping its taskbar button again. An application displays a button on the taskbar only if its primary window contains the WS_OVERLAPPED style. This is a very important consideration because, when the system is running low on power, it sends the WM_HIBERNATE message to all windows that have a button on the taskbar. If an application does not have a button on the taskbar it cannot receive and respond to this message.

Dialog boxes are secondary windows that contain controls. They simplify commands and provide information to the user about actions. If your application does not use the desktop metaphor, you may consider creating your interface using dialog boxes. They provide a great deal of flexibility when designing a non-desktop oriented window. Windows CE supports four types of dialog boxes: application-defined dialog boxes, common dialog boxes, message boxes, and property sheets.

An application-defined dialog box helps users perform tasks specific to an application. You can place controls directly onto the body of the dialog box or you can create a command bar on which you can place controls; do whichever is more appropriate for your application. Include only as many controls as are necessary and space them adequately.

A common dialog box provides a familiar way for users to perform standard tasks common to many applications. Windows CE supports the Color, Print, Open, and Save As common dialog boxes, which are not movable, and are always centered vertically and horizontally on the screen. A common dialog box always has the Help button displayed.

A message box is a modal dialog box that displays a message and prompts for input. It typically contains a text message and one or more predefined buttons.

A property sheet is a collection of tabbed dialog boxes that enables a user to view and modify the properties of an object.

In a desktop scenario, dialog boxes typically contain OK and Cancel commands that initiate a user's request or dismiss the window, respectively. In Windows CE, the X button represents both the Close and Cancel commands. Follow these guidelines for using the X and OK buttons in dialog boxes:

  • If the only buttons in a dialog box are the OK and Cancel (X) buttons, place them in the top right corner of the command bar, as they appear in a standard Microsoft Windows CE dialog box.

  • If a dialog box does not have an OK or Cancel (X) button, place the Close (X) button in the command bar. Place all other buttons in the body of the dialog box.

  • When the OK and X buttons perform the same function, use the OK button, since users are more comfortable selecting the OK button than the X button to confirm an action.

  • Never place an OK button both in the command bar and in the body of a dialog box, since many users find this confusing. You can, however, place a Cancel button in the body of a dialog box and an X button on the command bar, if you like.
