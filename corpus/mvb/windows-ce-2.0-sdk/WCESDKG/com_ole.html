COM and Automation

Microsoft object services may be classified into two main categories: Component Object Model (COM) and Automation (formerly known as OLE Automation). They are intended to make secure and reusable software component objects that are scalable, and inter-operable across heterogeneous platforms.

COM, as a programming development standard, forms a conceptual framework to define the component architecture. The COM library is a set of APIs that provide very basic object management services to facilitate the implementation of component design. Examples of such basic services include creation, deallocation, and lifetime control of component objects. To qualify as a COM object, the component must at least export and implement the IUnknown interface through which the component makes available its services.

Automation is a specific implementation of COM that allows software components to expose their features and functionality to other applications and to scripting tools. Automation provides a convenient means for application programs to interact seamlessly with each other. It enables an application developer to create applications and programming tools to expose component objects, to create and manipulate objects in one application by another, and to create tools to access and manipulate objects such as embedded macro languages, object browsers, and compilers.

When an object is exposed by an application or a tool, it is called an ActiveX object. The application or the tool becomes an ActiveX client. Automation enables an ActiveX client to programmatically manipulate an ActiveX object through the use of the IDispatch and/or IUnknown interfaces. These two interfaces provide two points of entry to access the member functions of an ActiveX object. In general, automation is capable of handling an ActiveX object residing in the same (DLL) or different (EXE) process as the client. However, in Windows CE they can be of in-process server type only (as a DLL). Thus, only CLSCTX_INPROC_SERVER may be passed to CoCreateInstance under Windows CE.

The Windows CE support of the object services is compatible with its desktop counterpart. General considerations apply equally in both cases. When it is applicable, most of the implementation specifics are very much the same. This document is intended to highlight the differences between the Windows CE and Windows NT implementations. It assumes that you are familiar with the COM and ActiveX Object Services chapter of the Microsoft Platform SDK Documentation.

The unique hardware features dictate that Windows CE streamline certain operations to save system resources. As no new functions are added, the Windows CE object services is a subset of the Windows 95/Windows NT object services. For instance, Windows CE uses CoInitializeEx to replace CoInitialize, CoInitializeEx and OleInitialize to initialize the COM and OLE libraries. Also, excluded from the Windows CE support is the Distributed Component Object Model (DCOM), which is designed to enable interprocess communications on different desktop host computers.
