COM Interface-Based Notification

In this method, two Component Object Module (COM) interfaces¾IDccMan and IDccManSink¾are used to register an application with Windows CE Services connection manager. The IDccMan interface is implemented by the Windows CE Services connection manager, while IDccManSink is implemented by the application. The advantage to this method is the control you get through the interface methods. However, it is more complex to use.

Note that when a connection is waiting to be established or has been established, an icon appears in the task bar (the icon shows two terminals with a connecting cable, next to the clock.). This icon indicates the connection status and also allows a shortcut (by right-clicking on the icon) to start the Explorer Window for Windows CE Services application.

The IDccMan and IDccManSink interfaces are defined in the header file Dccole.h, provided with the SDK. These interfaces are described in the topic "Connection Notification Interfaces".

Note The notification methods called by the connection manager vary slightly between Windows 95 and Windows NT. Under Windows 95, GW_LOG messages are sent under the control of the Direct Cable Connection (DCC) service. However, under Windows NT the connection manager simulates the GW_LOG messages.

Notification at Connection

The following procedure is for an application to be notified at the connection of the desktop PC and the mobile device. It assumes that the IDccMan and IDccManSink interfaces have been implemented.

  1. Initialize the component object model (COM) library and register with the Windows CE Services connection manager.
    1. The application calls the COM function CoInitialize to initialize the Component Object library.

    2. The application calls the COM function CoCreateInstance with the CLSID_DccMan class identifier and IID_IDccMan interface identifier, and receives a pointer to the IDccMan interface.

    3. The application calls the IDccMan::Advise method. This provides the Windows CE Services connection manager with a pointer to the IDccManSink interface implemented by the application. This also registers the client application with the connection manager.

    4. The Windows CE Services connection manager calls the IDccManSink::OnLogInactive method, telling the application that there is no connection between the desktop and the mobile device.
  2. Establish the connection between the desktop and the mobile device.
    1. The Windows CE Services connection manager calls the IDccManSink::OnLogListen method, waiting for the desktop PC and the mobile device remote connection services to run and respond. Until they are both running the connection manager will not proceed.

    2. For Windows 95 only, the connection manager calls the IDccManSink::OnLogAnswered method when the connection manager has detected the communications interface.

    3. The Windows CE Services connection manager calls the IDccManSink::OnLogActive method when the connection is established between the application and Windows CE Services connection manager.
    1. The Windows CE Services connection manager calls the IDccManSink::OnLogIpAddr method, providing the IP address for the communications socket which it obtained.

Note An application should not consider a connection to be completely established until the IDccManSink::OnLogIpAddr notification occurs.

  1. Perform the desired processing in the application.

Once the connection has been established, the application can begin normal processing. This can include processing on the desktop, remote processing on the mobile device (using RAPI), and calling the IDccMan methods.

It is advantageous to initialize RAPI (by calling CeRapiInit) when the IDccManSink::OnLogActive notification is received, since CeRapiInit requires that a connection be established between the desktop PC and the mobile device in order to return from the call.

An example of a useful IDccMan method is ShowCommSettings. This displays the Windows CE Services connection manager property sheet which allows the user to select the communication port for connecting the desktop PC to the mobile device.

Notification at Disconnection

The process for disconnection is similar to that of connection.

  1. Initialize the COM library and register the application (as shown above).

  2. When the actual disconnection occurs, Windows CE Services calls IDccManSink::OnLogDisconnection which tells the application that the connection has been terminated.
  1. Now application processing starts. It can only take place on the desktop PC.

Connection Notification Scenarios

You can see the results of several potential notification scenarios by using the Connection Notification Client sample program. After building and running the program, view the Notification Messages: listbox output in the Connection Notification Test dialog box. Some possible scenarios include: a new remote connection, a disconnection of the desktop PC or mobile device connection service, and a reestablishment of the remote connection.

The Unregistration Process

  1. The application calls IDccMan::Unadvise, which releases the memory associated with the IDccManSink interface

  2. The application calls IDccMan::Release, which releases the IDccMan object
  1. The application calls CoUninitialize to perform any OLE cleanup. Note: a call to CoUninitialize is required for each successful call to CoInitialize.
