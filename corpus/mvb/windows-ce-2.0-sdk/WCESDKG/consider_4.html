API Considerations

Windows CE supports and extends an essential subset of the Win32 API, while excluding functions that are not needed, or are redundant, for Windows CE devices. In addition to supporting Win32 API, Windows CE extends it in a number of ways. Most of these extensions are provided to support the unique capabilities of Windows CE devices. Some, such as the command-bar API, replace a set of Win32 functions, and implement their essential functionality in way that is more suitable for Windows CE devices.

Window CE does not support any 16-bit functions and some Win32 functions are not implemented completely, for example, a full range of styles or flags.

Windows CE is a Unicode environment. While it supports ASCII functionality to allow the exchange of text files, the native text format is Unicode. The following list provides guidelines for converting ASCII-base code to Unicode:

  • Include tchar.h. It has all the necessary conversions.

  • Use the Win32 string functions rather than the C run-time library equivalents.

  • Use TCHAR or LPTSTR for declarations. This allows the code to be compiled as either Unicode or ASCII.

  • Use the Text macro for string literals, such as Text("a string"). This allows the code to be compiled as either Unicode or ASCII.

  • Use sizeof(TCHAR) to ensure that your code is valid for both Unicode and ASCII when incrementing pointers, since a character no longer needs to be one byte long.

A further consideration is that the componentization of Windows CE means that many devices will support only a portion of Windows CE API. While all devices will share a common core API, there will be a great deal more variation between them than is the case with desktop PCs. You will need to determine exactly what is available on your target platform.

Windows CE includes a shell that has a look-and-feel that is similar to Windows 95, and currently found on the H/PC (see the Programming for the H/PC section for a complete discussion). However, it is not suitable for many Windows CE devices, and they will have their own shell. You will need to determine what shell is available on the particular device you are porting your application to.

In general, the most pronounced differences between Windows CE and Win32 APIs are in user-interface support. Because Windows CE devices often have a UI that is dramatically different from the desktop PC, your application's UI will probably have to be substantially or completely redesigned.

The ability to communicate with other computers is essential to the operation of many PC applications. Windows CE offers support for most standard forms of communication, including serial communication, TCP/IP and IrDA stacks (through WinSock), and support for output via modems, infrared transceivers, and local-area networks. Although all the features of the Win32 API are not supported, much communications-oriented code can be ported with relatively little modification.

Programs for Windows CE can be written in any of three languages, C++, Visual Basic, or Java. If your application was developed using a Microsoft Integrated Development environment, such as VB, VC++, or VJ++, you can continue to use it with Windows CE by installing the appropriate extension.

Many Win32 programs are developed using the Microsoft Foundation Classes (MFC), and the Active Template Library (ATL). Windows CE supports subsets of both of these tools. If your application was developed using either MFC or ATL, you may be able to port it, rather than beginning again.

Windows CE supports a subset of COM/OLE, a powerful and flexible approach to object-oriented programming that is used by many applications. You may be able to port a COM/OLE application to Windows CE.
