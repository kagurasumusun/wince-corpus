Implementing a Sample Transport Service

The SDK includes sample code for a transport service (located in the directory \Wce\Samples\Svcsampl) - see Svcsampl Sample. The Svcsampl sample transport service performs message service routines such as creating, writing to, and reading from files that are located in the Inbox. This is performed, for demonstration purpose, using file system functions such as CreateFile, ReadFile, and WriteFile. For transport functions that perform such tasks as sending, receiving, and deleting messages, a handle to a MailMsg structure is passed. The MailMsg structure contains the message header, body, and information about the message.

The sample transport service provided with the SDK sample code allocates a local heap (in TransportInit) for a transport-defined SERVICE structure that supports handling the messages, and provides a number of service functions to be used for message handling. For example, the sample service locates messages in a mail directory specified by the szMailDir field of the SERVICE structure. These messages are stored as individual text files; file names are simply numbers with a .txt suffix, assigned in sequence.

Every mail message that arrives on a server is given a persistent unique ID. This id is guaranteed to be different for every mail message and this ID never changes. However, these IDs are rather long (up to 70 characters) and are not too convenient to work with inside the transport service.

So, for each session, the service generates a non-persistent session ID to reference a long unique ID (see the TransportRecv function). Each time a connection is made to the server (that is, a POP3 session is created), the server looks at all of the currently stored messages and assigns a session ID to each message (numbered 1 thru the total number of messages). This makes it easier to reference a particular message without having to use its long unique ID. The drawback is that there is no guarantee that message number 5 (session ID is 5) on this session will still be message number 5 the next time the service is connected. So, the session ID can not be trusted from one connection of a service to the next reconnection of that service.
