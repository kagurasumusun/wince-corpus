Processes and Threads

As a multitasking operating system, Windows CE can support up to 32 simultaneous processes (where a process is defined as a single instance of an application). Multithreading support allows each process to create multiple threads of execution. Threads can operate independently, but belong to a particular process, and share the same memory space. The total number of threads is limited only by available physical memory.

Processes rely on Win32 messages to initiate processing, control system resources, and communicate with the operating system and user. These messages originate from a variety of sources, including the operating system; hardware events such as keyboard, mouse or touch screen activity; and other running processes or threads.

Each Win32 message consists of an ID (such as WM_PAINT), and two optional integer parameters (lParam and wParam) which can be used to pass additional information. Each process has its own message queue. Messages are placed in the appropriate queue associated and the process has a message loop that runs continuously, retrieving and handling messages in the order they arrive. Win32 messaging is discussed in detail in the Windows Platform SDK.

Within a process, there can be multiple threads of execution. Threads can function independently of each other, but they belong to the process, and share the same memory space. With multithreaded applications, each thread owns a message queue that is completely independent of other threads. Each thread will also normally have its own message loop to retrieve and handle messages. When there are no messages in the queue and the thread is not engaged in any other activity, the system suspends the thread, saving CPU resources.

Although threads can operate independently, they often need to be managed by the process. For instance, one thread may be dependent on another for a piece of information. Thread synchronization involves suspending a thread's execution until it receives a notification that it is ok to proceed.

Windows CE supports thread synchronization by providing a set of "wait objects". They allow a thread to block its own execution until a change in the wait object signals the thread that it is OK to proceed. Supported wait objects include critical sections, named and unnamed events, and named mutex objects. A detailed discussion of wait objects and their use can be found in the Windows Platform SDK.

Windows CE implements thread synchronization with a minimum of processor resources- an important point for many battery powered devices. Unlike many operating systems, the kernel itself handles thread related tasks such as scheduling, synchronization, and resource management. There is no need for an application to consume processor execution cycles polling for process or thread completion, or performing other wasteful, application-level thread management.

Windows CE is pre-emptive, which allows the execution of a process or thread to be pre-empted by one with higher priority. A priority-based, time-slice algorithm is used for thread scheduling. There are eight levels of thread priority. Listed from highest to lowest, they are:

  • THREAD_PRIORITY_TIME_CRITICAL

  • THREAD_PRIORITY_HIGHEST

  • THREAD_PRIORITY_ABOVE_NORMAL

  • THREAD_PRIORITY_NORMAL

  • THREAD_PRIORITY_BELOW_NORMAL

  • THREAD_PRIORITY_LOWEST

  • THREAD_PRIORITY_ABOVE_IDLE

  • THREAD_PRIORITY_IDLE

The THREAD_PRIORITY_TIME_CRITICAL setting is intended only for time-critical interrupts and should not be used unless absolutely necessary. Threads with this priority to cannot be pre-empted, and will run to completion.
