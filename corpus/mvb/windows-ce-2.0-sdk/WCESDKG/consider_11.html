Globalizing Windows CE Applications

If you plan to release your application in more than one language, you must keep language and cultural differences in mind when you develop specifications for the user interface and feature set. Consider the following potential trouble spots:

  • Text expansion. English text often grows when translated. In most cases, text increases by 10 or 15 percent; in some languages, localized text can be as much as 30-35 percent longer than the source text.

  • Use of abbreviations. In some languages abbreviations are not commonly used, for example in

  • Use of symbols, metaphors, and colors. Most have specific cultural meaning. Some common symbols in the United States may not be recognized or may be misunderstood in other countries-for example, a mailbox.

  • Text may be written and read from left to right, right to left,

  • Unique keyboard layout.

  • Use of an Input Method Editor. Chinese, Japanese, and Korean require one.

  • Word order and punctuation. Of particular concern are differences in the punctuation of currency and other numbers and the word order of dates. Though in English, word order is critical to meaning, in highly inflected languages, such as word endings are critical.

The time to address these concerns is in the design phase of your project. For example, you will be disappointed to discover-after your program is completed-that the Spanish word aceptar will not fit onto your application's OK button. Following are some tips.

  • Put all text strings that have to be translated in one location, such as a resource or text file.

  • Do not declare string buffers of an exact string.

  • Consider whether output is left to right or right to left.

  • Use the correct sorting method, date, time and currency representation for that locale.

  • Design controls, buttons and taskbar to accommodate different length text.

Windows CE makes your globalization efforts easier in two ways. Because Windows CE is a Unicode environment, all characters are double byte; therefore, you do not have to be concerned with manipulating both single byte and double byte characters.In addition, Windows CE includes National Language Support (NLS), which provides the NLS API as well as some font and keyboard functions for localization. For a list of the NLS functions suppored by Windows CE, see the end of this section.

The constraints of the device on which your application will run must beconsidered when globalizing your applicationThe following list describes some of the complex interactions between your application, a Windows CE device, and the needs of users in different countries.

  • The manufacturer of the device, not the application developer, determines what countries or locales to support.

  • Because a user does not log into the device, the user locale and the system, or default, locale are the same. For example, if you call the function GetSystemDefaultLangID or the function GetUserDefaultLangID you will obtain the same information.

  • The Windows CE operating system loads only one keyboard driver. Although it is possible to load a different keyboard driver, you would generally not do this because the device has a built in keyboard.

  • The locale can be changed by the programmer or by the user, through an application such as the Control Panel. Changing the locale often requires changing the font because the code page and character set change with the locale change.

  • Because RAM storage is limited on most Windows CE devices, it is not practical to install multiple fonts. Therefore, using a different font requires installing a new one, which can be time-consuming.
