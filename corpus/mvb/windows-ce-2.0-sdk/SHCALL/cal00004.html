Stack Frame Layout

The stack frame has the following layout:

The “Register Save Area” holds the preserved values of any permanent registers used by the function. It also contains the function’s return address.

The “Locals and Temporaries” area represents the stack space allocated for local variables and compiler-generated temporaries.

If a routine has alloca() locals, a separate frame pointer register is required to access the incoming arguments and locals. A leaf routine may use any free integer register as the frame pointer. A non-leaf routine must use a permanent register. The routine must not modify the frame pointer register between the prolog and epilog.

A routine may also establish a frame pointer to more efficiently access data in large stack frames. This is helpful on the SH-3 due to the limited size of the bit-field used to specify the offset in the register displacement addressing mode.

By convention, a routine that establishes a separate frame pointer should use R14, but this is not a requirement. Examples in this document often assume that R14 is the frame pointer.

The frame pointer typically points to a fixed frame offset in the RSA or Local and Temporaries areas of the stack frame, but may point to other offsets within the frame.

If a routine establishes no frame pointer, then R15 must remain unchanged between the end of prolog and the beginning of the epilog.

A leaf routine need not set up a stack frame for itself unless it needs to save permanent registers or allocate space for locals.

If a leaf routine does require a stack frame, it need not allocate stack space for outgoing arguments. Asynchronously invoked functions, such as signal and interrupt handlers, must make no assumption that all frames include four words of unused argument space since they may be invoked during the execution of a leaf routine which has no such argument space.

In a routine that uses alloca(), everything in the frame below (at a lower address than) the alloca() area is referenced relative to R15 and never contains a defined value at the time of an alloca() call. Thus, the alloca() operation never has to copy this part of the stack frame, and no data relocation problems arise. Everything in the frame above (at an address higher than) the alloca() area is referenced relative to the frame pointer.

A 4-word argument build area starting at the location pointed to by R15 in the stack frame must always be allocated by non-leaf functions, regardless of the number of arguments actually passed in calls from the function. This area is available for the callee to use for any purpose and is always assumed to be present.

The stack pointer and frame pointer addresses are aligned on four byte boundaries.
