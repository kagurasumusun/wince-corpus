Best Practices for Managing Performance in a Windows Mobile-based Application

Send Feedback on this topic to the authors

Before you begin developing your application, put together a plan for evaluating performance frequently and regularly during the development process. If possibly, evaluate performance on hardware that most closely resembles your retail device. Define your baseline performance criteria based on customer scenarios with your application. For example, require your application to open in less than one second, and for it to be able to render its window in less than 200 milliseconds (ms).

To thoroughly evaluate performance in your Windows Mobile-based application, profile manually, use the Remote Call Profiler, and use the Remote Kernel Tracker.

Profiling Overview

Profiling your code can provide information that you can use to refine the design of your application. It helps you identify bottlenecks in your application and it helps you optimize your application. Always use multiple methods when profiling your application.

Profiling Manually

Manual profiling is a low overhead way to get coarse data that provides the execution time of instrumented parts of your code. Instrument your code with GetTickCount, which provides millisecond granularity, and with QueryPerformanceCounter, which provides granularity dependent on the hardware platform. Hardware platform dependent granularity can be accurate up to one microsecond (μs).

The following table shows the advantages and disadvantages of manually profiling your code.

Advantages Disadvantages
  • Provides results with low overhead. You only need to add appropriate function calls and variables.
  • Allows an accurate representation of user scenarios because you are manually instrumenting the code.
  • Provides good data, especially on full retail code.
  • Provides coarse data.
  • Requires more work to get more granular data.
  • Provides data that includes time spent in other threads.

Using the Remote Call Profiler

The Remote Call Profiler provides relative profiling data with function call granularity. It has many options for user configuration to collect and view detailed data. Depending on the microprocessor, you may not be able to profile system-level code. For example, you cannot profile system-level code with an x86-based microprocessor, but with an ARM-based microprocessor, you can profile operating system (OS) functions. You cannot modify the OS functions, but you can view how much time they spend executing. Keep in mind that the Remote Call Profiler adds overhead, so the system is not guaranteed to run at full speed. You will have to recompile your application for the Remote Call Profiler.

The following table shows the compiler options to specify depending on the microprocessor of the hardware platform.

Microprocessor Compiler options
ARM-based
Note   With ARM-based microprocessors, you must link with CECap.lib.
 Can use either:
  • /callcap -Enable callcap profiling

    - or -

  • /fastcap - Enable fastcap profiling
x86-based
Note   These options apply to both physical and emulated x86-based microprocessors.
 Must use both:
  • /Gh - Enable _penter Hook Function

    - and -

  • /GH - Enable _pexit Hook Function
Note   The Remote Call Profiler does not profile managed code.

Instrument your code with the StartProfile and StopProfile functions to use the Remote Call Profiler. These function increment counters. You can also use the MarkProfile function to keep track of the location of the Remote Call Profiler in your application. Even though the Remote Call Profiler provides relative data, you should profile release builds of your application because profiling causes performance degradation. To obtain more absolute data than the Remote Call Profiler can provide, manually profile your code with the GetTickCount and the QueryPerformanceCounter functions. Use directives such as #ifdef around any code instrumentation so you can remove instrumentation code when you complete your application.

For more information about using the Remote Call Profiler, see How to Use Remote Call Profiler to Find Performance Problems.

Using the Remote Kernel Tracker

The Remote Kernel Tracker helps you understand how your application affects the entire system by providing very detailed system-wide information, such as when a thread blocks waiting for a semaphore, when an event signals, when an interrupt occurs, and any other system-event that passes through the kernel. This is useful for system-wide development, debugging device drivers and applications that communicate with each other, or for trying to balance the entire system. A system-wide view is useful because your application may not be directly degrading performance, but your application may be causing other parts of the system to degrade performance.
