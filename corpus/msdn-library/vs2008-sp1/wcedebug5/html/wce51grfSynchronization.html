Synchronization

Synchronization in automation guarantees that a UI action taken by automation code will be synchronous with the device. For example, if you click on a button in automation, the next UI action in your automation will not begin until the device has finished refreshing itself as a result of the button click.

Synchronization in DATK automation

Synchronization is implicit in DATK automation – whenever you use DATK to initiate a UI action, it will ensure that action is synchronous without any extra work on your part. By default DATK will wait for the system and the current foreground to become idle before returning from an UI action.

Special synchronization needs

Most of the time this implicit synchronization is sufficient, but if you have special synchronization needs for your automation you should deal with these at the Area Library level instead of in test cases. You can control the type of synchronization used by DATK by changing the global synchronization object. This object defines what heuristics DATK will use to determine that synchronization is complete. Available synchronization objects include:

  • SyncWaitForAllForegroundIdle – waits for all currently visible windows to become idle
  • SyncWaitForCurrentAppIdle – waits for all windows and threads belonging to the application in the foreground to become idle
  • SyncWaitForForegroundIdle – waits for the current foreground window to become idle
  • SyncWaitForNewForeground – waits until the foreground window changes and becomes idle
  • SyncWaitForForeground – waits until the specified foreground window (determined by process name or window finder) appears and becomes idle
  • SyncWaitForSystemAndForegroundIdle – waits for the all system threads to become idle and then waits for all foreground windows and threads to become idle
  • SyncWaitForSystemIdle – waits for all threads (not windows) in the system to become idle
  • SyncWaitForWindowIdle – waits for a specified window to become idle
  • SyncWaitForWindowIdleXTime – waits for a specified window to become idle and stay idle a specified amount of time

If you need to use a different synchronization object you need to swap out the current object before performing your UI action. The following method shows how you change synchronization objects:

/// <summary>
/// Example: change the implicit synchronization object
/// </summary>
public void ChangeSyncObjectExample()
{
    // Do work with default sync object

    // Change the sync object
    using(new SyncMode(new SyncWaitForSystemIdle(20000)))
    {
        // Do work with WaitForSystemIdle sync object
        // Inside this using block all implicitcit
        // synchronization is performed with the
        // SyncWaitForSystemIdle sync object
    }

    // Do work with default sync object
}

If you need to use a different synchronization object for an entire test suite you can swap out the sync mode in Begin and End as shown below:

    /// <summary>
    /// Example: Change sync mode for entire test suite
    /// </summary>
    public class SuiteSynchronizationExample : TestSuite
    {
        /// <summary>
        /// Example: Set the sync mode in Begin method
        /// </summary>
        public void Begin()
        {
            // Store the original sync object
            oldSync = Synchronization.GlobalActionSyncMode;

            // Replace the original sync object with new object
            Synchronization.GlobalActionSyncMode =
                new SyncWaitForAllForegroundIdle(
                Synchronization.defaultTimeout);

            // Other code that uses new sync mode
        }

        // Any number of test cases that use the new sync mode

        /// <summary>
        /// Example: Restore the sync mode in End method
        /// </summary>
        public void End()
        {
            // Restore the original sync object
            Synchronization.GlobalActionSyncMode = oldSync;
        }

        // private field to keep track of original sync object
        private SyncBasic oldSync = null;
    }

If implicit synchronization is not meeting your needs you can temporarily suspend it and make explicit calls to the synchronization. This should very rarely be necessary and is not encouraged. The following method shows how to work with explicit synchronization:

/// <summary>
/// Example: disable implicit synchronization
/// </summary>
public void DisableImplicitSyncExample()
{
    // Do work with default sync object

    // Change the sync object
    using(new SyncMode(null))
    {
        SyncWaitForSystemIdle systemIdle =
            new SyncWaitForSystemIdle(20000);

        // Inside this using block synchronization
        // will only be performed if you call it
        // explicitly

        // Perform UI action without synchronization
        systemIdle.Wait();
    }

    // Do work with default sync object
}

Changing the timeout for the global sync object

If you need to change the timeout for synchronization over a block of code you can use the SyncMode method explained in the previous question, specifying the desired timeout when you construct the new sync object. If you need to change the timeout for an entire suite you will need to set the global sync mode in the Begin method and reset it in the End method as show below.

/// <summary>
/// Example: changing sync timeout for suite
/// </summary>
public void Begin()
{

{

    // Restore the timeout

}

Custom synchronization objects

DATK allows you to enhance synchronization by creating your own custom synchronization object. This should rarely be necessary, and if you find you have need for a new synchronization object you should discuss this with the Tools Team to ensure that the work is not already planned.

Providing implicit synchronization for new DATK or MTK methods

If you are developing a new method for DATK or MTK that causes an action to take place on the device you are required to provide implicit synchronization. If your new method simply gets information without initiating any UI actions you do not need to worry about synchronization.

To provide implicit synchronization in your new method you need to use the AtomicAction object to wrap the lines of code that initiate the UI action. This serves to keep synchronization from occurring while the AtomicAction object is in scope, and to initiate synchronization when the AtomicAction object goes out of scope. The following method shows how to use AtomicAction to implement implicit synchronization:

/// <summary>
/// Example: implementing implicit synchronization
/// </summary>
public void ImplementingImplicitSyncExample()
{
    // Do work which does not initiate UI actions

    using(new AtomicAction())
    {
        // Do work to initiate the UI action.
        // Inside this using block synchronization
        // will not take place with the default
        // sync object. When the block is exited
        // the default sync object will be used
        // to synchronize the device.
    }

    // Do work which does not initiate UI actions
}
