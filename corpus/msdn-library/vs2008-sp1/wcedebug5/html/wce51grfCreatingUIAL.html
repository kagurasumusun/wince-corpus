Creating the UIAL

The UIAL projects for most applications have been created by software development engineers (SDEs) and software development engineers in test (SDE/Ts) working on feature teams. The UIAL projects will be maintained by area SDEs or SDE/Ts; as changes occur in the product UI the UIAL will simply be updated. This ensures that tests do not get out of sync from the product, since the people most familiar with changes to the UI own the test wrapper for the UI as well.

To a large extent the UIAL consists of generated code, but area owner expertise is needed to finish the process. The following are the general steps that are used to generate a UIAL. The work items listed are needed to complete the UIAL. When working with the UIAL, most of the classes representing dialogs will be automatically regenerated, so making changes to these files is wasted work. When changes are needed in these dialog classes, you need either to add tags to the associated RCML files or to extend the class that needs changes and make the changes in the inherited class. This is not the case with the classes representing applications.

Generate RCML files for dialogs

  • If you are generating a UIAL for Windows Mobile Version 5.0, you will need to build the RCML associated with your component. See Rebuild the RCML files for more information on this. This could take about 30 minutes.
  • If you are generating a UIAL for Windows Mobile 2003 second edition, you will probably want to integrate the RCML from Windows Mobile Version 5.0 into Windows Mobile 2003 second edition and then modify it to match your own UI. Talk with the Windows Mobile Version 5.0 developer about where to find the RCML files to integrate. It is recommended that you store them in private\qaapps\automation\AbstractionLayer\<app>\<product>\RCML in the Windows Mobile 2003 second edition branch. This could take about an hour.

Generate RCML files for other windows

  • RCML is only built for Dialogs. Other windows in your application (like the main window of your application) need you to take an RCML snapshot using RcmlSnap. You should do this for every window in your application that does not already have RCML. This could take 30 minutes to a few hours depending on how many other windows your application has.
  • Message boxes are also not generated by RCTOCS, but you should not use RcmlSnap to generate these. Instead, you should expose the generic Message Box class exposed in AbstractionLayer\Shell.

Rename controls in RCML to be semantically correct

  • See the section on Editing the RCML to find out how to do this. This could take about 15 - 30 minutes per file.

Generate your UIAL project

  • Run RCTOCS to generate the cs files for your application windows.
  • Run UialAppGen to generate the application class and self-test for your application.
  • Run AutoProjGen to generate a Visual Studio project for your UIAL.

Expose common dialogs through application classes

  • Some dialogs are shared by multiple applications and these will not be generated from RCML. However, these shared dialogs still need to be referenced from the application classes (or dialogs if they are owned by dialogs) that own them. You need to use RcmlSnap to get dialog classes for these and they will have to go in their own project so they can be shared with other apps. Work within your area to determine the structure here. Add the references to these dialogs just like the other dialog references in the application class. This could take about 30 - 60 minutes per dialog.

Reformat application and main window code to be semantically correct

  • UIALAppGen does not produce formatted code. To format your application class file (Microsoft.MobileDevices.AbstractionLayer.<app>.[<subapp>.]<product>.cs) open it in Visual Studio and do CTRL-A, CTRL-K, CTRL-F in sequence. Then rename all the controls listed in the comments at the top of the file following the same naming conventions used for RCML files. This could take about 15 - 30 minutes per file.

Unflatten Hierarchy

  • RCTOCS assumes that all dialogs are top-level. This is not always the case, as many applications have dialogs that have children which are also dialogs. In this case the reference to the child dialog needs to be moved out of the application class and into the dialog class of the parent. However, since you can not modify dialog classes themselves (except the main dialog class) you will have to inherit from them and move the child dialog references into the inherited class. This could take 15 - 30 minutes per dialog.

Expose IdnStrings

  • IdnStrings are a way to localize strings found in the product, so that test automation can be easily localized. RCTOCS will produce a skeleton file to hold your IDN strings called IdnHolders.cs along with the other classes for the UIAL. In this file you will find a class for each of the dialogs in your UIAL. The task here is to populate these classes with IdnString objects for strings that are exposed from your dialogs. Strings that don't belong to a single Dialog (such as menu text, menu item text, toolbar text, and soft key text) will go in the class dedicated to your app which is found at the top of the file. These will be developed over time, but right now they should expose toolbar and menu strings at least. Each class contains an example that will help you see how to create the IdnString object. Depending on the size of your area and the number of strings this could take a couple hours.

Manually write wrappers for nonstandard parts

  • Sometimes the product does not fit into the convenient scheme that RCTOCS tries to generate. In such cases, area owners with expertise in the product need to modify the UIAL. For instance, on the Contact form the user thinks they are simply typing a contact name into an edit box, when in truth that form only contains a List View that contains other controls. The UIAL should be modified to expose these fields in a way that makes sense to the end user (a tester writing test automation) instead of making them work through a list view. In most cases the needed changes will be in code that can not be edited by hand, so you will need to inherit the class that needs changes and make your changes in that inherited class. Only area owners will understand where in their UIAL things don't match up with expectations, and individual solutions to these issues will need to be discovered. The time for these items depends completely on how weird your area gets.

UIAL Self-Test

  • Every UIAL project has an auto generated self-test to smoke test the UIAL. You need to modify the test to open every dialog before calling the validation method on that dialog. Before passing the UIAL on to others for use we need to make sure that this passes. This will take a couple hours at least.

Area Libraries

  • Every UIAL will have a corresponding Area Library. Use AreaGen to generate the skeleton and then add a simple function that does a common set of steps that would occur in testing your area. Please write a function in here to get the process started for your test writers. This should take an hour or two.

Maintenance

  • Bug-fixes and feature additions to RCTOCS, as well as UI changes, will mandate regenerating code from RCML. UI changes should always be accompanied by appropriate changes to the UIAL tags in the RCML.
