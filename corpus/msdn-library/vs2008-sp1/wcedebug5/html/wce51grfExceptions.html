Exceptions

In general, you need to throw and catch the most specific exception applicable to your situation. It is practically never acceptable to throw or catch the base exception type (System.Exception). If you are throwing an exception you should find a class derived from System.Exception that meets your needs, or derive your own class from System.Exception. If you are catching an exception, you should only catch specific exception types that you can deal with.

The harness will catch all exceptions that are thrown from your code and log the test as a fail, so in your test or Area Library code you only need to catch exceptions that you need to deal with. You should not generally catch exceptions to determine whether to pass or fail a test case, or Area Library method. If you find you are only logging comments or setting a result flag inside your catch block, you should not be catching that exception.

Test cases should avoid using try and catch because this adds unnecessary complexity and makes the test cases difficult to read and maintain. In most cases, if a test case needs to catch an exception then the logic involved in causing the exception should be in an Area Library method instead. Area Libraries should catch exceptions when they can deal with them appropriately. For instance, if an area library method is performing several steps and it is possible for it to continue even though an early step fails, it might catch an exception from the earlier failure to ensure that it continues running.

Exception processing is very expensive in terms of run time. You should avoid throwing or catching exceptions to make decisions in your code whenever possible. Often if you find you are catching exceptions to determine whether a control exists, you should be using a property of the control to determine if it exists before accessing it. If you need a property like this and it does not exist, one should be created.
