Independent Test Cases

Having test cases that depend on each other can make your test suites inflexible and difficult to debug. For instance, if one test case depends on a previous test case to put the device in a certain state, that forces a dependency on the order of those test cases and means the latter test case cannot be considered valid if the former fails.The test cases should instead be independent of one another.

Test case independence offers a number of distinct advantages:

  • A test case can be executed by itself for debugging purposes, such as reproducing a failure. A simple command-line option can be used for that.
  • Independent test cases can be leveraged for stress, by executing them in random orders or repeating them randomly.
  • Independent test cases are easier to maintain; fixes or changes to one test case don't break another test case. The contract for a test case is much simpler when it is independent of other test cases.
  • Test failures are easier to debug when its success isn't linked to a trail of other test cases which must also succeed.
  • By being able to execute test cases independently, they can be distributed across multiple devices for higher throughput of test case execution.

When your test case fails, you will want to be confident that it failed because of a product bug or a bug in your own code. Debugging test failures becomes very difficult if you have to investigate the interaction of multiple test cases. If one test case fails it should not affect any of the other test cases in the test suite, and clean up code is a great way to ensure this (see the Test Case Cleanup section). Make sure your test case leaves the device in the same state that it started in.

The Begin and End methods provide setup and cleanup for entire suites (classes), not individual tests (methods). If you need to put the device into a particular state before running your test suite, you can use the Begin method. Simply override the Begin method in your test suite and have it do whatever configuration is necessary. This method will be run before any of the tests in your suite. Similarly, you can override the End method in your test suite to do any suite level cleanup. This method will run after all the tests in your suite have been run. The following is an example of overriding the Begin and End methods in your test suite:

/// <summary>
/// Summary description for BeginEndExample.
/// </summary>
public class BeginEndExample : TestSuite
{
      /// <summary>
      /// This will be run before any of the
      /// tests (methods) in this suite (class).
      /// </summary>
      public override void Begin()
      {
            base.Begin ();

            // Put any suite level setup code here.
      }

      /// <summary>
      /// This will run after all the tests (methods)
      /// in this suite (class) that will be run
      /// have been run.
      /// </summary>
      public override void End()
      {
            base.End ();

            // Put any suite level cleanup code here.
      }
}

For added flexibility, use the test case Initialization and CleanUp attributes discussed above. These can manage initialization and clean-up activities on a per-test case basis.
