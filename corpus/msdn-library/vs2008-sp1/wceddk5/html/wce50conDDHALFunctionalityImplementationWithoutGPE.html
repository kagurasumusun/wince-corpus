Implementing DDHAL Functionality without GPE

This topic describes the steps required to implement minimal DirectDraw hardware abstraction layer (DDHAL) functionality in your display driver without using GPE. This discussion assumes that you do not want to move an existing DDHAL from a Windows-based desktop platform to a Windows CE-based platform. For information about performing that task, see DDHAL Porting from the Desktop.

The source code for the sample display drivers is located in driver-specific subdirectories of %_WINCEROOT\Public\Common\OAK\Drivers\Display. The basic HAL source code is located in the %_WINCEROOT\Public\Common\OAK\Drivers\Display\DDGPE directory.

The following list shows the items you will need to implement a simple DDHAL in your display driver:

  • The build files used to export functions from your compiled code.

    This usually has the name of your compiled binary, as defined in the TARGETNAME=BINARYNAME section of your sources file, and ends with the .def extension.

  • The build files used to define include paths and to attach source code and libraries to your project.

    This file is usually called the sources file.

To implement DDHAL functionality without GPE

  1. Copy the Ddgpeusr.h header file from one of the sample driver's source directories, such as %_WCEROOT%\Public\Common\OAK\Drivers\Display\VGAFlat, into an appropriate location inside your display driver's build directory.

    This header file is private to your display driver and can be modified. You must customize this file to implement the IN_VBLANK and IN_BUSY macros because these are required by the sample DDHAL implementation.

  2. Copy the following source code files from the basic HAL source code into your display driver's build directory and add them to the appropriate build files:
    • HalCaps.cpp
    • HalDD.cpp
    • HalSurf.cpp
    • HalPalette.cpp
  3. Copy the DDHFuncs.h file from %_WINCEROOT%\Public\Common\OAK\Inc into your display driver's build directory.

    DirectDraw requires that your display driver export the HALInit function. You should modify the HalCaps.cpp file that you just added. It should implement HALInit. The following code samples shows the HALInit function prototype. 

    EXTERN_C BOOL WINAPI HALInit (
LPDDHALINFO lpddhi,
BOOL reset,
DWORD modeidx
);

    The HALInit function is normally responsible for setting up various global variables. It calls buildDDHALInfo with the appropriate parameters so it can make DirectDraw aware of the driver's support and capabilities. Because you are responsible for writing HALInit, you can add a variety of functionality.

  4. Modify the file used to export functions from your compiled binary to export the HALInit function that you created. To see how this is done, consult the sample driver source code file DDI.def.

    The most difficult part of this process is the actual implementation your DDHAL functions. For a list of functions that you must replace with your own implementation, consult Exported DDHAL Functions. Fill the appropriate HAL function stubs with your own code and modify the callback structures where necessary. For more information, consult the DirectDraw hardware abstraction layer specification.

    Note   Drivers should not expose the DDCAPS_CANCLIP flag, nor should they override the SetClipList function even if the device has hardware clipping. DirectDraw does not take advantage of hardware clipping directly. Instead, it relies on the GDI clipping engine.
  5. Modify the DDHFuncs.h header file to remove unneeded code.

    You should rename the header file to HalFuncs.h so it corresponds to the naming conventions of the other DDHAL source code files in your directory and does not conflict with the standard DDHFuncs.h that is part of DDGPE. Remove all GPE-specific global variables and function prototypes, and then add prototypes for any functions and global variables that you added and want to access elsewhere in your source code.

  6. Modify the driver initialization code to start DirectDraw support by loading the Ddstub.dll library.
  7. Compile and build your display driver to ensure that it continues to work properly.

    After you verify that it is still functional, your driver is ready to be tested with DirectDraw programs. Keep in mind that the code is not in an optimized state and requires some customization to improve performance. For more information, see DDHAL Customization.
