Implementing a ProtocolReceivePacket Handler

When an underlying NIC driver indicates an array of one or more packet descriptors with NdisMIndicateReceivePacket, NDIS will usually call a bound protocol driver's ProtocolReceivePacket function with each packet descriptor, thereby allowing the protocol driver or its clients to retain the packet descriptor and all resources it specifies until the protocol or its clients have consumed the data and returned the packet descriptor. The following list shows the two kinds of NIC drivers that typically call NdisMIndicateReceivePacket with an array of packet descriptors:

  • A NIC driver managing a busmaster DMA adapter that is capable of receiving several packets at a time into a ring of buffers
  • A NIC driver that provides OOB containing media-specific information, such as packet priority, in the NDIS_PACKET_OOB_DATA block associated with the packet descriptor

If a protocol driver is aware that it is or might be bound to such a NIC driver, it should have a ProtocolReceivePacket function. The following list shows the actions this function allows the protocol driver to perform:

  • Receive indications of full network packets from the underlying NIC driver.
  • Read the OOB associated with each packet descriptor using NDIS-supplied macros.
  • Retain ownership of the input packet descriptor and direct read-only access to the buffered data specified by the descriptor if the protocol makes copies of the data for its clients, or even to forward the indicated packet descriptor to its clients after selecting the range of packet data of interest to the clients.
  • Return the packet descriptor and the resources it described, possibly along with other retained packet descriptors, with NdisReturnPackets when the protocol has consumed the indicated data if it retains ownership of the input packet descriptor; otherwise, have clients return the packet descriptor if the protocol forwarded a receive indicator.

Even when a protocol driver provides a ProtocolReceivePacket handler, there are cases when a call by a NIC driver to NdisMIndicateReceivePacket results in a call to the protocol driver's ProtocolReceive function. Because a NIC driver temporarily relinquishes ownership of driver-allocated resources when it calls NdisMIndicateReceivePacket, the underlying driver depends on the consumers of those packets to return them in a timely manner. Otherwise, the NIC driver can run short of receive resources, such as receive buffer space in the NIC. When it does, the NIC driver sets NDIS_STATUS_RESOURCES in the OOB block associated with a packet descriptor in the packet array it passes to NdisMIndicateReceivePacket. Indicating a packet with this status causes NDIS to call the overlying driver's ProtocolReceive function with a packet and with any subsequent packets in the array. This forces the protocol driver to copy the packet data immediately rather than retain the NIC-driver-allocated packet resources.

If the protocol driver requires the OOB associated with a packet descriptor, but is called at ProtocolReceive, it must call NdisGetReceivedPacket and NDIS_GET_ORIGINAL_PACKET to copy the media-specific information into a protocol-supplied buffer, and possibly the TimeSent and TimeReceived values if the underlying NIC driver provides these time stamps.
