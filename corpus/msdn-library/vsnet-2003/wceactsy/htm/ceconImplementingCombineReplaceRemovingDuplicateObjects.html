Implementing Combine/Replace; Removing Duplicate Objects

Whenever the ActiveSync manager loses the mapping between desktop and device objects, it must prompt the user to either combine the desktop and device data, or to replace the device data with the desktop data. The following list covers causes that might make Combine/Replace necessary:

  • The user synchronizes a device with existing data for the first time.
  • The user deletes the device profile and reconnects the device to recreate a new partnership.
  • The user chooses a desktop store different from the one used in the last synchronization.
  • The user restores the device data from a backup file.
  • The user performs a Replace operation on one desktop computer, then synchronizes the device with a second desktop computer.
  • The persistent handles file is lost or corrupt.

If the user chooses Combine, all objects on the device and the desktop will be marked as changed.

If the user chooses Replace, all objects on the device are marked deleted and all desktop objects are marked changed.

During the subsequent synchronization, all changed items are kept, all deleted objects removed.

ActiveSync manager sets RSF_COMBINE in REPLSETUP::dwFlags when each object is to be synchronized. However, if the user cancels the synchronization or disconnects the device during the first synchronization, even though the process can continue properly in a subsequent synchronization, this flag will not be set again.

Choosing Combine often creates duplicate objects. It is highly recommend that an ActiveSync provider implement the IReplStore::RemoveDuplicates method. Following synchronization, the ActiveSync provider should use this function to find duplicate objects in the desktop store and prompt the user to remove them.

Once duplicate objects are found and removed, the ActiveSync provider can return control to ActiveSync manager, which in turn starts the enumeration of the store. It determines which desktop objects are to be deleted and sends commands to the device to remove the corresponding device objects.

A better implementation would avoid duplicating objects in the first place. This is possible if an ActiveSync provider has an efficient way to check when a device object is identical to an existing desktop object. When data for a device object arrives at the desktop, IReplObjHandler::SetPacket is called. If the device object is identical to an existing desktop object the ActiveSync provider can discard the packets without creating a duplicate object.

The provider also needs to tell the ActiveSync manager which desktop object the device object duplicated. It should set the RSF_DUPLICATED_OBJECT flag in the REPLSETUP structure that is passed to the IReplObjHandler::Reset method. Do not use the structure passed in IReplObjHandler::Setup. The provider should also set REPLSETUP::hItem to be the handle for the desktop object. All these operations are necessary so that ActiveSync manager can establish a mapping between the device and desktop objects.

Setting Synchronization Options

The ActiveSync Options feature lets users select a service provider and configure provider-specific options.

There is no standard user interface for setting options. The ActiveSync manager calls IReplStore::ActivateDialog so the ActiveSync provider can provide its own user interface. There are no requirements or limitations on the user interface — the developer is free to implement it in any way. If the ActiveSync provider does not support an option dialog, it should return E_NOTIMPL from IReplStore::ActivateDialog.

An ActiveSync provider should call IReplNotify::GetWindow to get a window handle that can be used as parent window of the dialog box or message box in which provider options will be displayed.

If the user changes an option that requires the ActiveSync provider to be reloaded (for example, changing the data store to be synchronized), IReplStore::ActivateDialog can return RERR_UNLOAD. ActiveSync then sets this provider in an error state. Synchronization for this provider will not proceed until the user disconnects and reconnects the device.

If the user cancels the Options dialog box, IReplStore::ActivateDialog should return RERR_CANCEL.

An ActiveSync provider can save its options in the registry or in the HREPLFLD handle. If saved in a HREPLFLD handle, the ActiveSync provider can set default option values in IReplStore::GetFolderInfo, where a new HREPLFLD needs to be created only if the pointer pointed at by phFolder is NULL. If the pointer is not NULL, the options are already loaded from the persistent ActiveSync data file.

If the device is not yet connected when the user clicks on Options, IReplStore::Initialize might not be called as the first method into the store. The ActiveSync provider needs to make sure IReplStore::GetStoreInfo does not return an error even when IReplStore::Initialize has not yet been called. A number of methods can be called before IReplStore::Initialize; you should be sure each of these methods works properly, whether or not Initialize has been called.
