Detecting Changes and Deletions with ObjectNotify

Using information in OBJNOTIFY, ObjectNotify determines whether the call concerns an object type the ActiveSync provider is interested in. Typically, an ActiveSync provider simply checks the flags and the file system ID in the OBJNOTIFY structure for the changed file-system object.

OBJNOTIFY is defined as follows.

typedef struct tagObjNotify
{
   UINT        cbStruct;     // structure size in bytes
   OBJTYPENAME szObjType;    // object type name
   UINT        uFlags;       // flags
   UINT        uPartnerBit;  // unused
   CEOID       oidObject;    // CEOID of changed/deleted file-system object
   CEOIDINFO   oidInfo;      // information about the file-system object
   UINT        cOidChg;      // change log
   UINT        cOidDel;      // delete log
   UINT       *pOid;         // ActiveSync provider owns the memory
} OBJNOTIFY, *POBJNOTIFY;

OBJNOTIFY::uFlags has the following definition.

Name Definition
ONF_FILE OBJNOTIFY::oidObject is a file.
ONF_DIRECTORY OBJNOTIFY::oidObject is a directory.
ONF_RECORD OBJNOTIFY::oidObject is a record.
ONF_DATABASE OBJNOTIFY::oidObject is a database.
ONF_CHANGED The file system object is changed.
ONF_DELETED The file system object is deleted. Only oidParent in OBJNOTIFY::oidInfo is defined. All other members in OBJNOTIFY::oidInfo are zero.
ONF_CLEAR_CHANGE The ActiveSync provider should mark the object up-to-date. In this case, OBJNOTIFY::oidObject is the synchronized object ID, not the file system object ID.
ONF_CALL_BACK Set by ActiveSync provider to ask ActiveSync manager to call back in two seconds.
ONF_CALLING_BACK Two seconds later, ActiveSync manager sets this flag and calls ObjectNotify.

If the file-system object contains any synchronized object, the ActiveSync provider should set OBJNOTIFY::pOid to point to a list of object IDs. A file-system object usually maps to a single synchronized object, so the ActiveSync provider can usually set OBJNOTIFY::pOid to be &OBJNOTIFY::oidObject.

ActiveSync manager calls ObjectNotify in the following cases:

  • Immediately after connection. The ActiveSync manager enumerates all file system objects and calls ObjectNotify for a list of synchronized-object IDs. Neither ONF_CHANGED nor ONF_DELETED is set. The ActiveSync provider should determine how many synchronized objects in the file-system object are changed and how many are up-to-date. It should set OBJNOTIFY::pOid to point to a list of object IDs, where the first OBJNOTIFY::cOidChg of them are changed object IDs and the next OBJNOTIFY::cOidDel of them are up-to-date object IDs. Typically, a file system object maps to a single synchronized object, so the ActiveSync provider simply sets OBJNOTIFY::pOid to be &OBJNOTIFY::oidObject. If the file-system object is changed, it sets OBJNOTIFY::cOidChg to 1 and OBJNOTIFY::cOidDel to 0. Otherwise, it sets OBJNOTIFY::cOidChg to 0 and OBJNOTIFY::cOidDel to 1.
  • When a file system object changes, as long as the device is connected. Either ONF_CHANGED or ONF_DELETED must be set. The ActiveSync provider should set OBJNOTIFY::cOidChg, OBJNOTIFY::cOidDel, and OBJNOTIFY::pOid as mentioned previously, except that OBJNOTIFY::cOidDel is the number of deleted synchronized objects.
  • After an acknowledgement is received from the desktop that the object has been synchronized successfully. The ActiveSync provider should mark the object up-to-date. In this case, ONF_CLEAR_CHANGE is set , but no other ONF_ flags (such as ONF_RECORD), nor any member in the OBJNOTIFY::oidInfo structure. The OBJNOTIFY::oidObject is the synchronized-object ID, not necessarily the file-system object ID. If your object ID is the same as the file-system ID, you can then call CeGetOidInfo to get information about this object and its parent object. The ActiveSync provider should mark the object as up-to-date so it will not be synchronized until it changes again.
  • ObjectNotify is called two seconds after ONF_CALL_BACK is set in a previous call to ObjectNotify. ONF_CALLING_BACK is set in this case.

Sending and Receiving Objects

Sending and receiving objects is implemented in the same way as for the desktop ActiveSync provider, using the same IReplObjHandler interface. All packets received are guaranteed to be in the same order and of the same size.
