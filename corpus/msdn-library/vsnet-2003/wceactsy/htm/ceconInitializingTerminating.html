Initializing and Terminating

IReplStore::Initialize ensures that the stock portfolio data file exists and is opened. The name of the file that needs to be synchronized is stored in the registry. ActiveSync manager determines the registry location for this file name.

The ActiveSync manager can manage multiple partnerships for different devices. Even if no device is connected, the user can select any one of the devices and set ActiveSync options, which might initiate the ActiveSync provider.

The bit flag ISF_REMOTE_CONNECTED is set if the device is remotely connected, such as through Ethernet or a modem. When implementing IReplStore::Initialize, if this flag is set, the ActiveSync provider should avoid using any blocking user interface, such as MessageBox or a dialog box, because the user will rarely be present to respond. The provider should instead take any default actions without prompting the user.

IReplStore::Initialize is usually the first IReplStore method called by the ActiveSync manager. In some cases other methods would be called first, especially when users need to change synchronization options for a disconnected device. The following is a list of methods that might be called before Initialize. All these methods must work correctly without Initialize being called first.

Method Purpose
IReplStore::GetStoreInfo Get information about a store. This information is displayed in the ActiveSync Option dialog box.
IReplStore::GetObjTypeUIData Get information about an object type. The information is displayed in the ActiveSync Option dialog box.
IReplStore::GetFolderInfo Give the ActiveSync provider a chance to see the folder handle (HREPLFLD).
IReplStore::ActivateDialog Let an ActiveSync provider to allow user to change options for a synchronization service.
IReplStore::ObjectToBytes Convert a HREPLITEM or HREPLFLD handle to a sequence of bytes.
IReplStore::BytesToObject Convert a sequence of bytes to a HREPLITEM or HREPLFLD handle.
IReplStore::ReportStatus Let the ActiveSync provider know about certain events.

The ActiveSync manager calls IReplStore::GetObjTypeUIData to retrieve object type-specific data for display in the ActiveSync status window. An ActiveSync provider must set up the given OBJUIDATA structure correctly. This structure is defined as follows.

typedef struct tagObjUIData
{
   UINT   cbStruct;      // size of this structure, in bytes
   HICON  hIconLarge;    // handle of a large icon used in the list view
   HICON  hIconSmall;    // handle of a small icon used in the list view
   char   szName [MAX_PATH];     // text displayed in the "Name" column
   char   szSyncText [MAX_PATH]; // obsolete in ActiveSync 3.0 and later
   char   szTypeText [80];       // obsolete in ActiveSync 3.0 and later
   char   szPlTypeText [80];     // obsolete in ActiveSync 3.0 and later
} OBJUIDATA, *POBJUIDATA;

The ActiveSync provider is unloaded automatically when the device is disconnected. The ActiveSync manager is typically the last to call IReplStore::Release. The provider reference count should reach zero and the interface can then be deleted. However, while executing, an ActiveSync provider might make calls to another party that increase the reference count of its own IReplStore instance, and the ActiveSync manager might not be the last to release the interface. The ActiveSync manager therefore always calls IReplStore::ReportStatus with RSC_RELEASE before calling IReplStore::Release. An ActiveSync provider can make sure all other external interfaces are released when RSC_RELEASE is received. This ensures that the reference count reaches zero when ActiveSync manager frees the store.

Enumerating All Desktop Objects

IReplStore::FindFirstItem is always the first function called in an enumeration. IReplStore::FindNextItem is then called repeatedly until the *pfExist flag returns FALSE, indicating there are no more objects to be enumerated. This terminates the enumeration, and ActiveSync calls IReplStore::FindItemClose. The ActiveSync provider is then responsible for "cleaning up" — freeing memory, deleting temporary objects, and so forth.

Objects can be lost when synchronizing a device with more than one computer. Objects not selected out during synchronization appear as deleted objects on the desktop. Desktop enumeration no longer returns these objects, so the ActiveSync manager commands the device to delete them. If two computers have different selection criteria, objects that are supposed to be retained on one computer will be deleted if they were not selected during a previous synchronization with the other computer.

To prevent this loss, the ActiveSync manager must know whether an object has actually been deleted or has only been deliberately omitted from selection. The ActiveSync provider should return every object in the store during enumeration, then use IReplStore::IsItemReplicated to implement selection. IReplStore::IsValidObject must return RERR_OBJECT_DELETED only if a handle representing a deleted object is passed.

All ActiveSync providers, regardless of whether they support real-time notification of changes and deletions, should set *pfChanged TRUE the first time the provider calls this API after a store is loaded. This forces ActiveSync to do an initial enumeration to determine if changes occurred while the device was not connected.

If an ActiveSync provider has an efficient way to detect whether an object is changed or deleted, it should implement that technique in IReplStore::IsFolderChanged. If IsFolderChanged sets *pfChanged FALSE when no object is changed or deleted, ActiveSync manager skips enumeration.

Typically, an ActiveSync provider sets a flag in IReplStore::GetFolderInfo for each folder. If this flag is set, IReplStore::IsFolderChanged sets *pfChanged TRUE and clears the flag. If the flag is not set, *pfChanged is always set FALSE.

An ActiveSync provider must be able to enumerate all objects in a given folder.

Detecting Changes or Deletions between Synchronizations

Each time an ActiveSync provider returns a new handle through IReplStore::FindFirstItem or IReplStore::FindNextItem, the ActiveSync manager searches the saved list for a handle that represents the same object. This matching process has three possible outcomes.

  • An enumerated handle matches a handle from the list.

    The ActiveSync manager calls IReplStore::IsItemChanged to see if the object has changed since last time it was synchronized. If it has, ActiveSync calls IReplStore::CopyObject to copy the data from the returned handle into the handle it saves. It then calls IReplStore::IsItemReplicated to determine whether the object should be replicated (copied) when synching to CE devices.

  • An enumerated handle fails to match any handle from the list.

    The enumerated object is new to the desktop, so a new object is created in the desktop store.

  • A handle from the list does not have a matching enumerated handle.

    The list object was deleted from the desktop. It should be marked for deletion from the saved list.

IReplNotify

The IReplNotify interface is implemented by the ActiveSync manager. It exposes the following methods:

  • OnItemNotify — Notifies the ActiveSync manager of object changes and deletions. Also notifies the ActiveSync manager to shut down the ActiveSync provider. This enables the manager to update synchronization status for the service provider in real time. If the service provider does not have the ability to detect real-time object changes/deletions, it can ignore this method.
  • SetStatusText — This function is obsolete.
  • GetWindow — Returns a window handle that is used as a parent window of any modal dialog or message box.
  • QueryDevice — Returns information about the selected device.

Reporting Changes or Deletions in Real Time

If an ActiveSync provider is implemented to detect changes in the desktop store as they occur, it can call IReplNotify::OnItemNotify to immediately notify ActiveSync. The provider should pass RNC_CREATED, RNC_MODIFIED, or RNC_DELETED to indicate the kind of change. The provider also passes a handle to the object, which allows the ActiveSync manager to search its own table for a matching device object.

Sending and Receiving ActiveSync Objects

Synchronization can be manually initiated by the user, automatically initiated when a CE-based device is connected to a desktop computer, or performed continuously whenever data on either connected machine changes (as implemented by an IReplNotify::OnItemNotify call).

Objects are copied from one machine to another by first being transformed into a byte sequence (serialized), then converted back into object format (deserialized). IReplObjHandler is the COM interface that performs these tasks. ActiveSync manager also uses this interface to delete an object from the store. IReplObjHandler is implemented on both desktop and the device so that much of the code can be shared. One instance of this interface is created for each object type.

There is no restriction on how an object can be converted to a byte stream. The ActiveSync manager guarantees the data will be sent in the correct sequence and properly reassembled into an object.

It is easy to serialize and deserialize StockPor data because only one packet is needed. The packet has the following structure.

// Data structure used to synchronize a stock used by IReplObjHandler
// on both the desktop and device. All strings are Unicode.

typedef struct tagStockPacket
{
   WCHAR     wszSym [10];
   WCHAR     wszCompany [80];
   WCHAR     wszLastPrice [20];
   WCHAR     wszPurDate [20];
   WCHAR     wszPurPrice [20];
   WCHAR     wszGain [20];
   FILETIME  ftUpdated;
} STPACKET, *PSTPACKET;

The following methods are always called in sequence whenever an object is converted into a byte sequence.

Method Purpose
IReplObjHandler::Setup Tell ActiveSync provider what object is to be serialized. Give it a chance to allocate any resource needed for serialization.
IReplObjHandler::GetPacket Let ActiveSync provider create one or more byte packets of any size. It is called repeatedly until RWRN_LAST_PACKET is returned.
IReplObjHandler::Reset Serialization is completed. Let ActiveSync provider release any resources.

The structure REPLSETUP is passed in IReplObjHandler::Setup. This structure is defined as follows.

typedef struct _tagReplSetup
{
   UINT         cbStruct;
   BOOL         fRead;
   DWORD        dwFlags;    // see RSF_ definitions
   HRESULT      hr;
   OBJTYPENAME  szObjType;
   IReplNotify *pNotify;

   DWORD        oid;
   DWORD        oidNew;

#ifndef UNDER_CE
   IReplStore  *pStore;
   HREPLFLD     hFolder;
   HREPLITEM    hItem;
#endif
} REPLSETUP, *PREPLSETUP;

The ActiveSync provider should pay attention to the following structure members.

  • fRead is set TRUE for reading an object from the desktop store and FALSE for writing an object into the desktop store.
  • dwFlags is a collection of bit flags related to object serializing/deserializing.
  • hFolder is a handle to the object folder.
  • hItem is the handle of the object to be serialized. ActiveSync should use the information contained in this handle to identify the object and convert it into.

All other members are internal to the ActiveSync manager and should not be changed.

Receiving an object from the device is similar to sending an object. IReplObjHandler interface methods are called to convert the data packets into an object, as shown in the following table.

Method Purpose
IReplObjHandler::Setup Tell ActiveSync provider which object to deserialized. Give it a chance to allocate resources needed for deserialization.
IReplObjHandler::SetPacket Send packets to ActiveSync provider so it can recreate the object. Packets are sent in the same number, size and sequence. SetPacket is called repeatedly until last packet is received from device.
IReplObjHandler::Reset Deserialization complete. The ActiveSync provider should release any resources.

The ActiveSync provider creates an object from the data packets. A new HREPLITEM representing the object is created and set in REPLSETUP::hItem.

Deleting ActiveSync Objects

Deleted objects sometimes require special attention. For example, when user deletes an e-mail message on the CE device, the message is actually marked as "changed" because it is moved to the Deleted Item folder. When the desktop ActiveSync provider receives notification, it has to decide whether to move its own copy of the message to the desktop's Deleted Item folder, or immediately delete the message.

In this case, the following special error codes can be returned by IReplObjHandler::SetPacket.

RERR_DISCARD The ActiveSync provider wants to delete the device object immediately after the change is synchronized. ActiveSync manager will send a command to the device object to delete the corresponding object.

RERR_DISCARD_LOCAL The ActiveSync provider wants to delete the desktop object immediately after the change is synchronized. ActiveSync manager will call IReplObjHandler::DeleteObject to delete the existing desktop object.

Resolving StockPor Conflicts

A conflict occurs when an object has changed on both the device and the desktop since the last synchronization. The conflict is resolved by prompting the user to choose which object to save.

When ActiveSync detects a conflict, IReplObjHandler methods are called to create a temporary copy of the device's object on the desktop. The ActiveSync manager then calls IReplStore::GetConflictInfo, passing the handle for the original desktop object and the handle for the temporary object. The ActiveSync provider fills in a CONFINFO structure to customize the text displayed in the Conflict Resolution dialog box. This structure is defined as follows.

typedef struct tagConfInfo
{
   UINT         cbStruct;
   HREPLFLD     hFolder;
   HREPLITEM    hLocalItem;
   HREPLITEM    hRemoteItem;
   OBJTYPENAME  szLocalName;
   TCHAR        szLocalDesc [512];
   OBJTYPENAME  szRemoteName;
   TCHAR        szRemoteDesc [512];
} CONFINFO, *PCONFINFO;

The Conflict Resolution dialog box offers the choice of discarding the original desktop object or the device object. The discarded object is marked as up-to-date — unchanged since the last synchronization — while the kept object retains its "dirty" — changed — status. In the subsequent synchronization, the "changed" object overwrites the "unchanged" object.

Regardless of which object is chosen, IReplObjHandler::DeleteObject is called to delete the temporary object.

To resolve a conflict

  1. On detecting a conflict, the ActiveSync manager sends a command to the device's ActiveSync provider to read the object.
  2. IReplObjHandler::GetPacket is called on the device to serialize the object and send the packets to the desktop ActiveSync provider.
  3. IReplObjHandler::SetPacket is called on the desktop to create a temporary object from the deserialized packets. The HREPLITEM handle created for this object is returned to the ActiveSync manager.
  4. The ActiveSync manager places the handles for both objects in the CONFINFO structure in a call to IReplStore::GetConflictInfo. The ActiveSync provider can use these handles to extract information from the objects and save them in CONFINFO.
  5. Using the description text returned in the CONFINFO structure, ActiveSync manager displays the standard Conflict Resolution dialog box.
  6. If the user chooses to keep the object on the device, the desktop object is marked up-to-date.
  7. If the user chooses to keep the object on the desktop, the device object is marked up-to-date.

    If the user cancels the dialog box, nothing is done and conflict resolution for this item will begin again at the next synchronization.

  8. IReplObjHandler::DeleteObject is called to delete the temporary object.

ActiveSync manager sets the RSF_CONFLICT_OBJECT flag in all calls to IReplObjHandler methods.

If the ActiveSync provider cannot or does not want to write a temporary object in Step 3, it can save the packets in memory and return a HREPLITEM with a pointer to the memory. To the ActiveSync manager, this handle is like a handle to an object. To the ActiveSync provider, this handle is a special one that represents packets of data. The provider needs to make sure this type of handle is properly implemented in all IReplStore methods that take an HREPLITEM handle (for example, CopyObject, FreeObject). When IReplStore::GetConflictInfo is called, CONFINFO::hRemoteItem will be this special handle. The ActiveSync provider can then extract descriptive text from the handle and save it in CONFINFO.

The ActiveSync provider can be written to resolve conflicts by itself, without prompting the user to make a decision. The following error values can be used in the implementation of IReplStore::GetConflictInfo to guide conflict resolution:

  • RERR_IGNORE Using the two handles in CONFINFO, the ActiveSync provider recognizes that the objects are identical, so there is no need to prompt the user to select one. The ActiveSync manager resolves the conflict by setting both as "up to date."
  • RERR_DISCARD The desktop object is already deleted. ActiveSync manager issues commands to the device to delete the device object.
  • RERR_DISCARD_LOCAL It is assumed the device object is the newer version, so the local (desktop) version is deleted. This is potentially dangerous, but it is a reasonable assumption if changes almost always occur to device objects, but rarely to desktop objects.
