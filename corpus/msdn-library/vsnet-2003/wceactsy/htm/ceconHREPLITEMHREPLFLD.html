HREPLITEM and HREPLFLD

The HREPLITEM handle, a 32-bit number created by the ActiveSync provider, uniquely identifies one object. Whenever the service manager needs information about an object, it calls IReplStore or IReplObjHandler methods, passing the object's HREPLITEM handle.

HREPLITEM is typically a pointer to an internal structure or a class instance. In the StockPor ActiveSync provider, it is a pointer to a CItem instance, which contains a 32-bit object ID and a time stamp for the last modification made to the object. Calling IReplStore::FindNextItem or IReplStore::BytesToObject always creates a new HREPLITEM handle for the newly enumerated item or the item recreated from the byte sequence.

Because HREPLITEM contains an object ID, the ActiveSync provider can determine whether two handles represent the same object. If HREPLITEM also contains a change number or time stamp, the ActiveSync provider can determine which of two handles represents the more-recent version of an object.

There must be an ordered relationship between handles representing different objects. The sample-code implementation of IReplStore::CompareItem compares object IDs. It returns 1 if the first handle is bigger than the second, –1 if the first is less than the second one and 0 if two are equal. Because IReplStore::CompareItem is called frequently, it must be implemented efficiently. Ordered handles allow the ActiveSync server manager to use a binary search, rather than having to check every item in the table of handles.

The ActiveSync provider does not have to synchronize all objects of a given type. Using selection criteria, it can choose which ones are to be synchronized — appointments that occur within the next three weeks, for example.

Selection is implemented through IReplStore::IsItemReplicated. The ActiveSync provider can use the data in the HREPLITEM handle, or open the object and read related data so the selector can be applied.

If the object is not to be replicated, the ActiveSync provider returns FALSE. The ActiveSync manager issues commands to delete all non-replicated objects on the device. The corresponding objects on the desktop are not touched.

HREPLFLD is a handle to an object type, often called a folder. In the StockPor ActiveSync provider, HREPLFLD is implemented as a pointer to an instance of the CFolder class. Because the StockPor ActiveSync provider supports synchronization of just one object type, only a single instance of the class needs to be created in IReplStore::GetFolderInfo.

The ActiveSync manager knows nothing about the contents of the handle. When the handle is not longer needed, ActiveSync calls IReplStore::FreeObject to give the ActiveSync provider a chance to free whatever resources are used by the handle. If ActiveSync needs to copy the data from one handle to another handle representing the same object, it calls IReplStore::CopyObject. ActiveSync needs to periodically confirm that the handle still represents an valid — undeleted — object, so it calls IReplStore::IsValidObject.

Data stored in HREPLITEM and HREPLFLD handles is automatically saved to a persistent file created and maintained by ActiveSync. An ActiveSync provider implements IReplStore::ObjectToBytes to serialize (convert to a byte stream) HREPLITEM and HREPLFLD handles, and IReplStore::BytesToObject to deserialize (convert back to a handle) the same byte sequence.

The persistent file is read immediately after a device is connected, so that all handles used in the previous synchronization can be recreated. Upon device disconnection, ActiveSync converts each handle back into a series of bytes and writes all handle data into the persistent file.

ActiveSync manager keeps a unique data file for each device partnership, and makes sure the correct file is loaded for the connected device. This process is transparent to the ActiveSync provider.

Store Information and Store Identifiers

An ActiveSync provider must be able to determine if the store it synchronizes now is the same store used in last synchronization. If it is different, mapping between desktops and device objects must be re-established using Combine/Replace. Combine combines all desktop and device objects. Replace replaces device objects with desktop objects. Combine can create duplicate objects, which an ActiveSync provider should be able to detect and remove. See Implementing Combine/Replace; Removing Duplicate Objects for other cases where Combine/Replace is required.

ActiveSync calls IReplStore::GetStoreInfo to retrieve information about a store, including the store identifier. This store ID can be any size and the complete ID is stored in the persisted ActiveSync data file. Immediately after the device is connected, the ActiveSync manager reads this ID and passes it to IReplStore::CompareStoreIDs. An ActiveSync provider must be able to tell if the current store ID matches the one loaded from the ActiveSync file (which identifies the store used in previous synchronization).

The structure STOREINFO is passed to IReplStore::GetStoreInfo. The structure is defined as follows.

typedef struct tagStoreInfo
{
   UINT    cbStruct;           // structure size in bytes
   UINT    uFlags;             // miscellaneous flags; see SCF_ definitions
   TCHAR   szProgId [256];     // program ID name of the store object
   TCHAR   szStoreDesc [200];  // description of the store
   UINT    uTimerRes;          // enumeration interval in microseconds
   UINT    cbMaxStoreId;       // maximum size of store ID
   UINT    cbStoreId;          // actual  size of store ID
   LPBYTE  lpbStoreId;         // pointer to store ID
} STOREINFO, *PSTOREINFO;

If IReplStore::CompareStoreIDs returns a value other than 0, the ActiveSync provider discards the persisted replication handles because they are assumed to be no longer valid. ActiveSync then prompts the user to decide whether information on the device should be integrated with the new store or discarded in favor of the new data.

The STOREINFO structure returned by the provider also controls the method ActiveSync uses to determine when the desktop store is changed. ActiveSync providers that support real-time change notification through the IReplNotify callback interface should set the SCF_SIMULATE_RTS bit in STOREINFO::uFlags.

ActiveSync providers that do not support real-time change notification should set STOREINFO::uTimerRes for the desired behavior. If uTimerRes is 0, the ActiveSync manager starts enumeration when the ActiveSync status window is activated by the user, or immediately before synchronization. If the uTimerRes value is non-zero, the ActiveSync manager automatically starts enumeration every value microseconds.

To get back a variable-size store ID, the ActiveSync manager calls IReplStore::GetStoreInfo first with STOREINFO::cbMaxStoreId set to 0. The ActiveSync provider should set the required size for a store ID in STOREINFO::cbStoreId and return E_OUTOFMEMORY. The ActiveSync service manager then allocates memory and passes the pointer in STOREINFO::lpbStoreId, which is used by the ActiveSync provider to save the store ID.
