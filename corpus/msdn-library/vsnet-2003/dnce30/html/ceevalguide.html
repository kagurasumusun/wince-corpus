Introduction

Microsoft® Windows® CE Platform Builder 3.0 delivers all the tools you need to rapidly build Windows CE-based embedded systems, including the latest version of the Microsoft Windows CE operating system (OS). Platform Builder's integrated development environment (IDE) enables you to configure, build, and debug a new generation of highly modular designs that combine the flexibility and reliability of embedded systems with the power of Windows and the Web. New IDE features such as improved target-host integration and connectivity for faster embedded development, advanced system-level debugging support including hardware-assisted and source-level debugging, and an improved extensibility model for directly integrating additional microprocessor architectures and third-party tools, allow you to quickly and easily build customized solutions. Platform Builder now also includes the eMbedded Visual Tools 3.0, which offers versions of the familiar desktop tools Microsoft Visual Basic® and Visual C++® optimized for embedded application development.

The following table explains key Platform Builder features.

Building a Basic Platform

Developing a custom Windows CE operating system involves building a basic platform, downloading the OS image to a target device, and debugging the OS image. Platform Builder also enables you to customize your platform. For more information, see Customizing a Platform later in this document.

To simplify the development process, Platform Builder provides both an integrated development environment (IDE) and command-line tools. You can use either the command-line tools or the IDE to create your platform. Additionally, the IDE provides wizards and tools that you can use to modify, build, localize, debug, and export your platform.

The easiest way to create a basic platform is to use the IDE tool, called Platform Wizard. Through a series of interactive dialog boxes, Platform Wizard lets you select microprocessors your platform will support and choose whether to use a preconfigured board support package or create one. Platform Wizard gives you several options for selecting an OS configuration, and then sets up the environment with files that support the selected OS configuration.

Kernel Debugging

Once you've downloaded an OS image, you can debug it. Platform Builder 3.0 provides a kernel debugger which debugs code in the Windows CE kernel as well as Windows CE–based applications. The enhanced debugger user interface in Platform Builder includes new debugging windows and menu items that enable you to acquire process, thread, and other target debugging information.

Using EXDI Hardware-Assisted Debugging

Platform Builder allows you to use EXDI hardware-assisted debugging to control the execution of a target device, and to examine and modify the state of the device. Third-party vendors provide the required hardware and software, which at least includes a driver and either a probe or an emulator. The third-party vendor may also provide a target device, or the target and probe may be one piece of hardware with a software plug-in that adds hardware-specific functionality to the debugger. Platform Builder provides an IDE interface for the third-party components.

To use EXDI hardware-assisted debugging, you must install the third-party EXDI driver on a development workstation running Platform Builder, and connect a probe or emulator between the development workstation and the target device. The driver multiplexes communication between the probe or emulator and all clients, including Platform Builder and debugger plug-ins. The same driver can sometimes support multiple microprocessors, even those from different microprocessor families.

The following illustration shows a typical EXDI hardware-assisted debugging configuration.

The EXDI driver works solely with the debug support available on the hardware, and does not rely on an OS for this support. In doing so, the hardware debugger can work even if the OS is not fully functional, or even if there is no OS on the target device. The hardware debugger can debug initialization phases such as hardware setup, boot loading, and OEM adaptation layer (OAL) initialization, as well as OAL routines and the kernel itself. You can also use it to debug other kinds of code, although the kernel debugger may be more appropriate and is recommended.

Customizing a Platform

Platform Builder enables you to customize different elements of a Microsoft Windows CE platform. You can utilize core components from a third-party OS configuration, add or remove components, localize the platform, and create a board support package, OAL, and boot loader.

Platform Builder provides two board support packages, one for a Hitachi D9000 hardware development platform (ODO) and one for a Windows CE PC-based hardware development platform (CEPC). These board support packages appear as choices when you use the Platform Wizard to create a platform. You can also create your own board support package and add it to a platform. For example, you might want to create a board support package to work with a specific hardware configuration. A board support package contains an OAL, device drivers, and a default component list for your custom hardware.

When you add components to your platform, you can either choose components provided by Platform Builder or create your own. You can generate applications, dynamic-link libraries such as device drivers, static libraries, and a transport layer.

A device driver links an OS and a device so that they recognize each other and the device can be used in applications. A transport layer is used to communicate between a host computer and a connected device. You need a transport layer to export a custom software development kit (SDK).

After refining and debugging the platform on the hardware development platform, you adapt it for your custom target device. Platform Builder helps you create a boot loader and an OAL, which are necessary before you can download your OS image to your custom target device.

Creating an OEM Adaptation Layer

An OEM adaptation layer (OAL) is the layer between the Windows CE kernel and the target device. This layer facilitates communication between your Windows CE–based operating system and your target device.

Before you begin creating your OAL, you must first create a Windows CE kernel that contains all the features you want to support, such as debugging and profiling. Once you have created a kernel, you are ready to create your OAL.

You create the OAL by implementing functions that communicate between the kernel and device hardware such as serial ports, parallel ports, Ethernet hardware, and timers. The OAL also includes hardware interrupt handling and power management interfaces as well as boot-time hardware detection and initialization. Once the OAL is complete, you statically link it with the kernel.

OAL architecture can vary significantly from one target device to another. However, all OALs perform the same essential function of allowing your Windows CE–based platform to control the core system hardware of your target device. The following table shows the recommended stages of OAL creation.

Stage Description
1. Initializing the kernel In this stage, you perform the steps that are necessary before creating an OAL, such as designing your reference platform and updating the Config.bib file. The goal of this stage is to configure your resources, such as memory layout, that are required for the microprocessor to function.
2. Creating a base OAL In this stage, you initialize your platform at startup, enable the serial port for debugging, initialize communication settings, and establish a system tick. The goal of this stage is to provide basic system initialization code that will support further debugging and to ensure that basic kernel initialization is complete and consistent with the target device requirements.
3. Enhancing OAL functionality In this stage, you implement interrupt service routines (ISRs), manage the clock and timers, configure debugging options, enable power management, and provide platform information for applications. The goal of this stage is to implement the remainder of the platform support functions and ensure that a full OS boot is possible.
4. Completing an OAL In this stage, you implement any additional features. For example, you can log processes, create a driver development kit (DDK), define extension memory, erase the object store, support high-resolution timers, and configure the registry.

For more information about creating an SDK, see Exporting a Software Development Kit later in this document.

Using Hardware-Assisted Profiling

Windows CE supports several profiling techniques to measure operating system performance on a target platform, including hardware-assisted profiling. Windows CE supports this profiling technique by including an application programming interface (API) library that supports process-level tracking. You can use this library to write an application that is notified when a process or thread is created or terminated, or when a thread is scheduled to run.

You can use the information that the system passes to the application to perform custom profiling functions. To enable hardware-assisted profiling, assign function addresses to global pointers in the OAL. The kernel uses these pointers to pass information to the functions that you implement in the OAL.

Exporting a Software Development Kit

When you've finished customizing and debugging your platform, you can download the final OS image to your custom target device. The next step is to provide support for the development of additional applications for the platform. Platform Builder enables you to create a software development kit (SDK).

Platform Builder combines a series of modules and components to create a software platform that runs on a custom hardware device. These modules and components include core OS components, OAL components, and other run-time libraries. Many of these components, such as the run-time libraries for MFC for Windows CE, contain APIs that you can use to gain access to the capabilities of your target platform. Windows CE offers you the familiar environment of the Microsoft Win32® API, Microsoft ActiveX® controls, message queuing (MSMQ), Component Object Model (COM) interfaces, and ATL.

You can use Platform Builder to create an SDK based on the Windows CE OS that allows developers to write applications that run on your target platform. An SDK is a set of library, header, and help files that developers use to write applications for a specific platform. The SDK summarizes the information that is necessary to create and debug an application on your target platform. This information includes headers, libraries, help documentation, Platform Manager components, run-time files, and platform extensions.

After you create an SDK, you can move it to another computer. To create, debug, and run custom applications, other developers can use your SDK along with Microsoft eMbedded Visual Tools 3.0, which includes Microsoft eMbedded Visual Basic 3.0 and Microsoft eMbedded Visual C++ 3.0.

Microsoft eMbedded Visual Tools use the SDK to determine which menus, files, and debugging applications to display to a developer who is creating software for the target platform. These tools also use the Platform Manager components to decide how to transfer information from the computer to the target platform through the transport layer.

Because Platform Builder tracks the core OS modules that belong to a given platform, you do not need to describe the modules that the associated SDK should support. Instead, Platform Builder automatically incorporates into your SDK the necessary headers and libraries for the modules that make up your platform.

You can include a technology in your platform but exclude it from your SDK. For example, you can include support for MFC in your OS, but choose not to expose the MFC APIs in your SDK. By limiting support for some technologies, you can reduce the size of your SDK. You can later export an SDK that includes support for technologies that you previously excluded.

The SDK Roller automatically creates a platform-specific HTML help file. This file contains information about the APIs supported by the exported SDK. When you install the SDK to the eMbedded Visual Tools, documentation appears in the help collection beneath a node with the name of the exported SDK.

You can also include custom documentation in your SDK. Custom documentation appears under the node called “Microsoft Windows CE” in the Table of Contents for the eMbedded Visual Tools help files.

The SDK export process produces a self-extracting executable file (.exe) containing the SDK for your target platform. You can run the .exe to install the SDK on another computer.
