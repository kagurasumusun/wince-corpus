Sample HID Class Driver

The USB HID (Human Interface Device) is a USB client driver and does not directly interface with any hardware; therefore it has no PDD and no DDSI. It uses the USB driver interface to communicate with the USB host controller and the physical device. Because the HID driver manages devices typically controlled by other drivers, the DDI is a combination of available DDIs.

The sample HID class driver in %_WINCEROOT%\Public\Common\OAK\Drivers\USB\Class\HID.

This USB device driver supports the joystick, game pad, mouse, and trackball Human Interface Devices (HID).

The following list shows the three parts that constitute the HID driver's DDI:

  • An interface for sending mouse events, mouse_event.
  • An interface for sending keyboard events, keybd_event.
  • Set of I/O controls to allow Microsoft® DirectInput® API to manage devices.

In order to present applications with a consistent method of accessing those devices, the HID class driver uses the DirectInput. It uses the stream interface functions to interact with the DirectInput subsystem.

In the sample, the registry keys are configured to load the drivers automatically; plugging in an HID class device such as a mouse or keyboard loads the HID class driver.

The following series of actions takes place when a user connects an HID device such as a mouse or keyboard to a platform that contains the HID class driver. After the HID class driver is loaded and the USB driver module calls the driver's USBDeviceAttach function, the driver calls an initialize function that opens a pipe to the HID device's interrupt endpoint. It also starts a worker thread to handle interrupts. This thread enters a loop in which it submits interrupt transfers by calling the IssueInterruptTransfer function. After the transfer completes, the driver retrieves the event data from the function's lpvBuffer parameter. It then creates an appropriate mouse or keyboard event to submit to the input system and the DirectInput subsystem.

The HID class driver submits input to both DirectInput and the input system for two reasons. One is so that DirectInput is not required to be present in a platform just to use the HID class driver. The other is that if an application that is using DirectInput to access the mouse or keyboard fails or stops responding, the use of those devices is still available to other applications. The sample HID class driver presents itself to the DirectInput subsystem as a stream interface device, with the special device file name HID1:. The device file name prefix is typically HID.

The DirectInput subsystem in uses I/O control codes to request various actions from the HID class driver. The following table shows the eight I/O control codes that the HID class driver must support in its IOControl function.

I/O control code Description
IOCTL_HID_ACQUIRE Notifies the HID class driver that the DirectInput subsystem wants to receive events connected to a handle that was previously obtained through use of the IOCTL_HID_SET_FORMAT control code.
IOCTL_HID_ATTACH Notifies the HID class driver that an application needs to use a device.
IOCTL_HID_ENUM_DEVICES Returns a list of devices that the HID class driver is currently managing.
IOCTL_HID_ENUM_OBJECTS Returns the number of input sources, such as buttons, on the device.
IOCTL_HID_GET_INST_DATA Returns data from the device to the DirectInput subsystem.
IOCTL_HID_POLL Requests that the HID class driver poll the device to get the device's status.
IOCTL_HID_SET_FORMAT Sets the format of data that the HID class driver returns for a device to the DirectInput subsystem, and acquires the device for use by an application.
IOCTL_HID_TRANSFER_EVENT Registers an event handle that the HID class driver can use to notify the DirectInput subsystem when the device generates data.

The implementation of the DirectInput subsystem for is a subset of the full DirectInput API that is defined for desktop versions of Microsoft® Windows®. The following differences between these implementations affect the HID class driver:

  • DirectInput for Windows CE supports only foreground-exclusive mode. Therefore, only one thread at a time in the system can use the sample HID class driver.
  • DirectInput for Windows CE does not support force feedback mechanisms.
  • Attempting to enumerate the available HID class devices fails if there are no such devices connected to the Windows CE–based platform because the USB subsystem unloads the HID class driver when there are no HID class devices to control.
