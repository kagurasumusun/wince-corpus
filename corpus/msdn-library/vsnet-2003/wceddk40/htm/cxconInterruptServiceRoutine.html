Interrupt Service Routines

The kernel calls interrupt service routines (ISRs) based on the call to HookInterrupt, and the ISR returns an interrupt identifier. For more information on interrupt identifiers, see Defining an Interrupt Identifier.

An ISR might move data from a CPU register or a hardware port into a memory buffer, but in general, it should not attempt to do a lot of work. Instead, it must rely on a dedicated interrupt thread called the interrupt service thread (IST) to do the bulk of the required processing. When more processing is required, the ISR lets the kernel know this by returning a logical interrupt value other than SYSINTR_NOP. In the example shown here, the return value from the ISR is SYSINTR_KEYBOARD.

The ISR maps a physical interrupt number to a logical interrupt value. For example, the keyboard might be associated with hardware interrupt 4 on one device and hardware interrupt 15 on another. The ISR, which is in the platform-specific OAL, translates the hardware-specific value to the Windows CE standard value of SYSINTR_KEYBOARD.

When an ISR notifies the kernel of a specific logical interrupt value, the kernel examines an internal table to map the logical interrupt value to an event handle. An event is a standard Win32 synchronization object that serves as an alarm clock to wake up a thread when something interesting happens.

The kernel wakes up the dedicated IST, which has been waiting on an event, by calling the Win32 function PulseEvent.

The following table compares the situation with a single ISR and multiple ISRs.

ISR model Description
Single ISR On all Windows CE–based platforms that support a single ISR, the name of the ISR is OEMInterruptHandler. The role of the ISR is to examine an interrupt and determine how to handle it. An ISR needs to be extremely fast; otherwise, it slows down the operation of the device and the operation of all lower priority ISRs. An ISR must look at the cause of the interrupt to decide how to handle it. In some cases, an ISR might decide that no further handling is required because the device is disabled or data is being buffered. Nevertheless, an ISR notifies the kernel with a SYSINTR_NOP return value that no further action is required.
Multiple ISR A system that supports multiple ISRs is a system that has multiple hardware interrupts on its CPU. The OAL can register handlers for each of these interrupts by calling the HookInterrupt function in the kernel. This function builds a table that maps hardware interrupt identifiers to specific ISR functions. When there are multiple ISRs supported, the OAL does not provide an OEMInterruptHandler function. Other than having to map from an IRQ to an interrupt service routine, handling interrupts with multiple ISRs is identical to handling interrupts when a single ISR is present. Another reason not to process data in the ISR is that there is no way to access the user buffer. The user mode IST routine can access this buffer.
