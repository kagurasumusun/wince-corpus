IEEE 1394 Virtual VCR Drivers

The Virtual VCR Subunit stands as an example of how a Virtual Subunit might be written. It is only one form of implementation, favoring a certain type of design. It is not intended to be a pure tutorial or a completed module suitable for release in a commercial product.

The Virtual VCR Driver could have been implemented one of two straightforward ways. With the first model, the model is broken into two components. The first component is the WDM-based Virtual Subunit Driver, AVC_VVCR. This component deals with the underlying protocols responsible for managing a Virtual Subunit and a Virtual VCR Subunit in specific. It does not, however, actually carry out any tasks related to streaming media or emulating a VCR. Instead, those tasks are handled by the second component, the Virtual VCR Application. The application deals with media, streaming, emulating a tape mechanism, Stop, Rewind, Fast Forward, Play, and so on, and depends on the AVC_VVCR Driver, or the underlying AVC_STREAM driver, to carry out the details in its high-level tasks. Quite specifically, part of the processing is done inside a WDM Driver, and part of the processing is done inside of an application.

With the second model, all of the functionality of the Virtual VCR is encapsulated within the Virtual VCR Driver. No application is involved. All of the processing is done within a WDM Driver.

Both models have advantages. The first model is more convenient to application writers, who wish to limit their understanding of the internals of IEEE 1394. It also does not hardcode a particular Virtual VCR Mechanism emulation or implementation, and extends actual control of the Virtual VCR Mechanism directly to the Application. The second model's primary advantage is that it is much simpler to write. Breaking asynchronous events and tasks across the boundary between WDM and Applications while taking into account issues such as that an application could exit without ever completing all pending AV/C Requests presents some painful design issues, not to mention a significant amount of code to act merely as glue.

The Virtual VCR Driver as provided in Microsoft® Windows® CE .NET actually implements the first model. This is neither a recommendation that other Virtual Subunits be necessarily implemented in the same manner, nor a recommendation not to. The developer should take their needs into account before deciding on an implementation strategy.

AVC_VVCR is only included in an IABASE or HLBASE build, that is, the module itself and the registry entries associated with enabling it in the WDM hierarchy, if the configuration environment variable SYSGEN_1394_AVC_VCR_VIRTUAL is set at the time when Sysgen is processed.

IEEE 1394 Virtual VCR Driver API Definition

The API set for the Virtual VCR driver is primarily the APIs defined by the Streaming Filter Driver and IOCTLs related to control of the Virtual VCR. As many asynchronous operations can be occurring at once, it is recommend that consumers of the Virtual VCR Driver make generous use of Overlapped I/O, a feature typically invalid for Windows CE, but supported by WDM and all of the associated IEEE 1394 device drivers. The following table shows the Virtual VCR IOCTLs.

IOCTL Description
IOCTL_VVCR_COMPLETE This control code permits the caller to complete asynchronous requests previously returned to the caller from IOCTL_VVCR_EVENT.
IOCTL_VVCR_EVENT This control code permits the caller to receive notifications from the virtual VCR Driver about events that have occurred.
IOCTL_VVCR_QUERY_STATE This control code permits the caller to iterate through the plugs preallocated by the driver due to registry settings.
IOCTL_VVCR_SET_MECHANISM_POSITION This control code permits the caller to notify the virtual VCR driver of the tape's current position.
IOCTL_VVCR_SET_MECHANISM_STATE This control code permits the caller to notify the virtual VCR driver of the tape mechanism's current state.
IOCTL_VVCR_SET_MECHANISM_TRACK_NUMBER This control code permits the caller to notify the Virtual VCR Driver of the tape's current track number.
