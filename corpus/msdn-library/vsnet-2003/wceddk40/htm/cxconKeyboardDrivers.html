Keyboard Drivers

The keyboard driver converts input from the keyboard hardware into keyboard events that the driver enters into the input system. The driver is also responsible for generating the proper Unicode characters from these keyboard events. The keyboard driver is divided into components, which facilitate development of keyboard drivers for international keyboard layouts. Some keyboard drivers need to have keys generate multiple virtual keys. This is useful on smaller platforms that do not have the all of the physical keys normally present on desktop workstations. Some of the keys have multiple function, modified functions, or both. The driver generates virtual keys based on the state of particular physical keys and modifier keys such as SHIFT, ALT, and so on.

Generally, you should implement the keyboard driver as a layered driver. The upper layer, or MDD, maps scan codes to virtual key codes, generates character data associated with VK codes, and then packages keyboard messages and puts them in the system message queue. The lower layer, or PDD, retrieves scan codes from hardware.

The keyboard driver is different from other device drivers in that it is language dependent. The ScanCodeToVKeyEx function is responsible for translating between hardware dependent scan codes and standard Windows virtual keys. This function will be dependent on the particular hardware and keyboard layout for the language. The KeybdDriverVKeyToUnicode function is responsible for generating the correct Unicode character based on the state of the virtual keys. This function is dependent only on the keyboard layout for the language. Both of these functions are based on translation tables; also known as, keyboard mappings, which you can customize for different languages. You can create your own Keyboard Mappings or customize the existing keyboard mappings, if necessary.

The input system loads the keyboard driver at startup time. When the input system starts, it retrieves the name of the keyboard driver dynamic-link library (DLL) from the HKEY_LOCAL_MACHINE\Hardware\DeviceMap\KEYBD\Drivername registry key. If no entry is found, the input system uses the default name, Keybddr.dll. It then loads the DLL and verifies that all required entry points exist. Then, the input system calls the KeybdDriverInitialize function to perform a one-time initialization. In this function, the driver saves a local copy of the input system callback function. The KeybdPdd_InitializeDriver function is also called to perform any hardware-specific initialization. It then starts the interrupt service thread (IST) to handle keyboard interrupts. This thread calls the InterruptInitialize function to register an event for the SYSINTR_KEYBOARD interrupt. It then waits for the event to be signaled. When the event is signaled, the IST calls the KeybdPdd_GetEvent function. It then sends the key events returned from the lower layer to the input system using the callback function provided by the input system when the KeybdDriverInitialize function was called. The input system pulls the keyboard event from the queue and calls back to the driver's KeybdDriverVKeyToUnicode routine. The driver analyzes the specified key event and the virtual key state and generates the corresponding characters. The input system then sends the virtual key and the characters to the appropriate application. The keyboard driver must add the flags KEYBD_DEVICE_SILENT or KEYBD_DEVICE_SILENT_REPEAT to the virtual key codes it submits to the input system in order to suppress audible key clicks.

The KeybdDriverGetInfo and KeybdDriverSetMode functions get and set information about the keyboard. When the main input thread processes a keyboard-connection event, the thread calls the KeybdDriverGetInfo function to get the virtual-key-to-Unicode data supplied by the driver. The thread also allocates the required memory for the virtual key state data and any extra data required by the driver. Next, it calls the KeybdDriverInitStates function to initialize the memory.

The KeybdDriverInitializeEx, KeybdEventCallbackEx, KeybdPdd_GetEventEx, and KeybdPdd_InitializeDriverEx functions replace the non-EX versions of these functions. The Ex functions provide support for Terminal Server Client by handling extra scancode information that the Terminal Server Protocol requires. The sample keyboard drivers on all platforms use the Ex versions. For more information on sample keyboard drivers, see Keyboard Driver Samples.

When the keyboard IST wakes up to service a keyboard interrupt, there is a call to KeybdPdd_GetEventEx to retrieve the generated keyboard scan codes and the translated virtual key codes.

For each valid keyboard event, the IST checks if a key is pressed or released. If a key is pressed, it calls KeybdDriverRemapVKeyDownEx to handle virtual key remapping. If a key is released, it calls KeybdDriverRemapVKeyUpEx.

In KeybdDriverRemapVKeyDownEx, the function checks to see if the virtual key is a numeric keypad key and if the NUMLOCK key is active and a SHIFT key is pressed. If true, the function remaps the keypad virtual key to fake SHIFT key releases in the remap virtual key buffer. Then, adds a virtual code for the keypad key when the NUMLOCK key is not active.

When you release the keypad key, KeybdDriverRemapVKeyUpEx is called. The function sends the keypad key release. Then, it re-enables the original SHIFT key state by sending fake SHIFT key presses.

The following table shows the upper layer, or MDD, keyboard driver functions.

Function Description
KeybdDriverGetInfo Retrieves information about the keyboard and driver.
KeybdDriverSetMode Sets mode information for the keyboard device.
KeybdDriverInitialize Performs a one-time-only keyboard driver initialization.
KeybdDriverInitializeEx Performs a one-time-only keyboard driver initialization.
KeybdDriverVKeyToUnicode Generates the appropriate Unicode characters and shift state flags for a specified virtual key, key state array, and driver state.
KeybdDriverInitStates Initializes the virtual key state and driver specific state.
KeybdDriverPowerHandler Handles system power-state change notifications.

The following table shows the lower layer, or PDD, keyboard driver functions.

Function Description
KeybdPdd_DllEntry Called by the upper layer on DLL state changes.
KeybdPdd_GetEvent Called by the upper layer to retrieve keyboard events after the SYSINTR_KEYBD signal is sent.
KeybdPdd_GetEventEx Called by the upper layer to retrieve keyboard events after the SYSINTR_KEYBD signal is sent.
KeybdPdd_InitializeDriver Called by the keyboard driver upper layer to initialize the keyboard hardware.
KeybdPdd_InitializeDriverEx Called by the keyboard driver upper layer to initialize the keyboard hardware.
KeybdPdd_PowerHandler Called by the upper layer on system power state changes.

The following table shows other keyboard driver functions.

Function Description
KeybdEventCallback Prototype of the callback function passed to the KeybdDriverInitialize function.
KeybdEventCallbackEx Prototype of the callback function passed to the KeybdDriverInitialize function.
