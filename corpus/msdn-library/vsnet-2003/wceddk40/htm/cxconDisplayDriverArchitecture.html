Display Driver Architecture

Display drivers are loaded and called directly by the graphics, windowing, and event subsystem (GWES.exe). Windows CE–based display drivers are most commonly written using a layered architecture because of the number of hardware-independent operations. The Graphics Primitive Engine (GPE) library handles all of the default drawing, acting as the display driver's model device driver (MDD) upper layer. You write the hardware-specific code that corresponds to the display driver's lower layer (the PDD).

The following table shows the modules that make up the Windows CE graphics pipeline.

Module Description
Application An application must be present to cause graphic output to appear on the display screen. It can be as simple as a typical Hello World program, or as complex as a 3D engineering application. Whichever it is, it calls into GDI. Coredll.dll exposes these functions.
Coredll.dll The major set of functions is exposed through a single DLL, called Coredll.dll. In most cases, this library does not do the work itself. Instead, this library packages up the parameters for the function call, then triggers a local procedure call (LPC) to another process. The specific process to be called depends on the specific function call. All drawing and windowing calls are sent to GWES.EXE.
GWES.exe The GWES process is responsible for all graphical output, and all interactions with the user. Among the drivers that reside in the GWES address space are display drivers, printer drivers, keyboard drivers, mouse drivers, and touch screen drivers.
DDI.dll The default name for the display driver is DDI.dll. As with most DLLs, the outside world communicates through exported functions. DDI.dll exports a single function, DrvEnableDriver, which returns to the caller a pointer to an array of 27 function pointers. When GWES has work to do with a display driver, it calls one of these 27 functions. Writing a device driver involves writing the code for these 27 functions. Three of these functions are specific to printer drivers, which leaves 24 for display driver developer to deal with.
Hardware The graphic pipeline ends at the hardware. The display driver communicates to the hardware using whatever mechanism required by the hardware. This typically involves a combination of memory-mapped video buffers and I/O registers.

Display driver writers can minimize the amount of time and effort that is needed to create a display driver by customizing one of the sample drivers provided with Microsoft® Platform Builder. All of the sample drivers take advantage of the GPE class to provide default drawing with hardware-specific issues.

The GDI makes calls to the display driver and the display driver writes to the physical display device. All Windows CE–based display drivers must implement a set of display DDI functions, which you use to initialize the display driver and draw to the display.

The GPE classes serve as a base of code that you can use to derive new display drivers for your hardware. The GPE classes handle all communication within the display DDI layer and handle all of the default drawing. Using the GPE classes can save you a large amount of development and debugging work. All the sample display drivers use the GPE. They demonstrate how you can add extensions to the display driver, for example, to enable hardware accelerations. If you decide to use the GPE classes, you will have to provide code necessary to ensure that your display device operates correctly. In addition, if your device supports some kind of hardware acceleration for BitBlt transfers, you can also enable it. Be aware that using the GPE classes involves hardware requirements. The GPE classes are for display devices that support a flat-frame buffer. Flat-frame implies that all the display device memory must be in a single block of contiguous memory.

All display driver controls write to the built-in display hardware of the system. This hardware can be an LCD screen, but it can also be any sort of display hardware that is suitable for your platform. The display driver model for built-in display hardware is the same as the model for peripheral display adapter drivers.

Create a registry key under HKEY_LOCAL_MACHINE\Drivers\Display to store configuration entries for your display driver. The initialization routine of your display driver should create keys under HKEY_LOCAL_MACHINE\Drivers\Display\Active so that applications can determine which display devices are available.

PCI-based display drivers can benefit from the PCI bus driver loading model. The PCI bus driver and/or the platform's BIOS enumerates and programs the PCI configuration space of the device and populates the registry with configuration information. The display driver can then read this registry information without having to scan the bus for its device and read the PCI configuration space itself. For an example of this, refer to the DisplayInit and MapPhysicalDevice functions for the MQ200 driver in %_WINCEROOT%\Public\Common\OAK\Drivers\Display\MQ200\Devmap.cpp.

GWES writes the driver that it is using into HKEY_LOCAL_MACHINE\System\GDI\Drivers\MainDisplay. GWES determines which display driver to load by following these steps:

  1. GWES checks the list of candidate displays in HKEY_LOCAL_MACHINE\System\GDI\DisplayCandidates to see if any are instantiated on the local system. If so, GWES takes the first one it finds, for example, the one with the lowest number. This list is usually set up in Platform.reg.
  2. GWES checks HKEY_LOCAL_MACHINE\System\GDI\Drivers. This value explicitly names the display driver.
  3. GWES attempts to load Ddi.dll, which is the default display driver name. A registry entry in Common.reg loads Ddi.dll. A dedicated process can load secondary drivers by calling CreateDC("MyDDI.DLL").

GWES allows you to create OS images that determine the display adapter at run time based on PCI instance data for example, and load the appropriate driver. If it is possible that no display adapter is present, you can use Ddi_nop.

For example, assume that a device could have TVIA5000 or Permedia3 displays in PCI slots. The system could also run in a headless configuration with no display adapter. You can create an image to support this by setting BSP_DISPLAY_TVIA5000=1, BSP_DISPLAY_PERM3=1, and BSP_DISPLAY_NOP=1. You also need to create PCI templates and a GDI candidate list in your Platform.reg file. If the PCI bus driver detects a display adapter card, it will create a PCI instance key that GDI will use to load the driver. If no adapter cards are found, the Ddi_nop driver will be loaded because it appears after the others in the following registry example.

IF BSP_DISPLAY_MQ200
[HKEY_LOCAL_MACHINE\System\GDI\Drivers]
    "Display"="ddi_mq200.dll"

;        
;MediaQ MQ200 driver settings
;
[HKEY_LOCAL_MACHINE\Drivers\Display\MQ200]
   "Rotate"=dword:0
   "PPSupport"=dword:0
   "PPSupportEnable"=dword:0

;; 640x480x16
   "CxScreen"=dword:280
   "CyScreen"=dword:1E0
   "BPP"=dword:10
   "Freq"=dword:3C

;; FB_BASE address
   "FB_BASE"=dword:00000000

;; OEM run time flag
   "Flag"=dword:00030503

   "MIU2"=dword:00EA0086
   "MIU3"=dword:6C4848C4
   "MIU5"=dword:00000119
   "DC0"=dword:0EF2082A
   "PLL1Freq"=dword:00530000
   
   "PWM"=dword:000000A1
        
[HKEY_LOCAL_MACHINE\Drivers\Display\MQ200\Color]
;; Cursor Color setting
   "CC"=dword:F

;
; Add power manager for MQ200 displays
;
[HKEY_LOCAL_MACHINE\Drivers\BuiltIn\PMDDI]
   "Prefix"="DDI"
   "Dll"="pmddi.dll"
   "Order"=dword:1

;
; MQ200 supports saving/restoring video memory surfaces during suspend/resume.
;
[HKEY_LOCAL_MACHINE\SYSTEM\GWE]
    ; "PORepaint"=dword:0 - the display driver handles everything
    ; "PORepaint"=dword:1 - gwe should save and restore the bits
    ; "PORepaint"=dword:2 - gwe should invalidate and repaint
    ; "PORepaint"=dword:3 - gwe and driver need to save video memory
    ;
    "PORepaint"=dword:3
