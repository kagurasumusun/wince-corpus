Driver Loading with the PCI Bus Driver

The PCI bus driver is responsible for enumerating the PCI bus and then loading device drivers for any of the devices it finds.

The PCI bus driver first enumerates the PCI bus by scanning for devices and enumerating the resources required by the devices. These resources include memory base addresses, I/O base addresses and IRQ numbers. A configuration routine provided by the driver can be used at this point to configure non-PCI compliant resources as well as extension ROM resources. The PCI bus driver assigns resources to each of the devices and then a second enumeration pass is run to match the devices with registry entries found under the PCI\Template key. The PCI bus driver also looks for matches under the PCI\Instance key to look for exact matches, see Device Driver Loading Process for details. The device is matched to a registry entry by applying a best-fit algorithm to the registry entries shown in the following table.

Entry Description
Class Identifies the basic function of a device, for example, a mass storage controller.
SubClass Identifies a specific sub-class of basic function, for example, an IDE controller.
ProgIF Identifies a register-specific programming interface, for example, USB OHCI or USB UHCI.
VendorID Identifies the manufacturer of the device.
DeviceID Identifies the type of device.
SubsystemVendorID Identifies the vendor of a card or subsystem that uses a device.
SubsystemID Identifies the type of card or subsystem that uses a device.

The identifiers are listed in order of increasing specificity. When matching a found device with a registry entry, all of the values that are listed in the registry must match the found device. For example, a driver that works with all 16550-compatible serial controllers would list the values shown in the following table.

Entry Descriptions
Class The value for simple communications controllers.
SubClass The value for serial.
ProgIF The value for 16550-compatible serial controllers.

If a particular serial driver were tailored to a particular vendor's device, then the VendorID and DeviceID values would be listed as well. The registry entry for this driver would only match a device that contains the exact same Class, SubClass, ProgIF, VendorID and DeviceID. The VendorID, DeviceID, SubsystemVendorID and SubsystemID can have a list of values associated so the driver can be matched with a subset of cards. If lists are used, they must all be of the same length.

Once a match is found, the template information is copied over to a PCI\Instance key, along with the additional resource information such as MemBase, MemLen, IoBase, IoLen and Irq. An IRQ to SYSINTR mapping is requested at this time from the OAL, and the SYSINTR is written out the registry instance key SysIntr.

At this point, the driver is loaded with its newly created instance key. The driver now has all of its configuration information contained in the registry, so it no longer needs to enumerate the bus to discover its corresponding device.
