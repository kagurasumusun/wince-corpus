Device Driver Development

Device drivers, which are included in every Microsoft® Windows® CE operating system (OS) image, are responsible for direct communication to devices.

A device is a physical or logical entity that requires control, resource management, or both from the operating system (OS). A device driver is a software module that manages the operation of a device, a protocol, or a service. A device driver also manages virtual, or logical, devices. A virtual device exposes a physical device interface, even though there is no physical device associated with the device interface. A device driver for a virtual device is indistinguishable from a device driver for a physical device. In this context, virtual means that there is no physical device to manage, but a device-like interface is being exposed. File system drivers are examples of virtual device drivers.

Typically, you can characterize drivers by the device interfaces they expose. In the simplest case, there is one interface exposed downward to the hardware, and one interface exposed upward to applications. You can refer to the interface exposed to the hardware as the hardware interface or the bus interface. The interface exposed to applications is the device interface or client interface. You can use the device interfaces to characterize the driver. Applications, other drivers, or the Device Manager can manipulate the device interfaces. The provider of that interface determines how those modules manipulate the client interface. For more information, see Device Interface Classes.

Buses are responsible for loading the drivers for the devices on their buses. Bus enumeration is the process of examining the bus and then loading the appropriate drivers. The root bus driver is a registry enumerator. A call to ActivateDeviceEx invokes the root bus driver; the Device Manager does this automatically. Bus drivers are responsible for determining which other drivers to load, and in what order to load them. For more information on driver loading, see Device Driver Loading Model.

Different processes load different drivers. The following table shows the processes that load drivers and what drivers they load.

Process Drivers
Graphics, Windowing, and Events Subsystem (GWES.exe) Battery drivers, display drivers, notification LED drivers, printer drivers.
Device Manager (Device.exe) Audio drivers, keyboard drivers, mouse drivers, NDIS drivers, serial drivers, PC Card drivers, USB drivers, and any other driver that exposes the stream interface.
File System (FileSys.exe) File system drivers.

Generally, devices connected to the system do not influence drivers and applications. The specific interfaces, which the drivers for those devices provide, influence drivers and applications. For example, Explorer.exe does not need to be informed that a new block device has appeared as a result of PC Card insertion, it needs to be informed when the file system volumes on that card are mounted. This causes the Device Manager to send notifications for all of the driver's defined interfaces after the driver is loaded and initialized, and then again after the driver is unloaded. For more information, see Device Interface Notifications.

Device Driver Source Code

The device driver source code is separated into platform dependent code, CPU support package (CSP) drivers, and common drivers. This directory structure allows you to copy a public driver to your platform directory, and then optimize and test the driver as necessary. For information on testing drivers, see Driver Testing.

The following table shows the layout of the device driver source code.

Path Description
%_WINCEROOT%\Platform\%_TGTPLAT% This platform dependent code is specific to given platforms or standard development boards (SDBs). This directory is mainly the OAL, configuration files, and BSP drivers. You should not have to modify the platform dependent drivers in %_WINCEROOT%\Platform\%_TGTPLAT%\Drivers.
%_WINCEROOT%\Public\Common\OAK\CSP These are CSP drivers for high-integration microprocessors or microprocessor companions with many native peripherals integrated onto the microprocessor. CSP drivers include microprocessor-specific OAL drivers for real-time clocks, timers, debug Ethernet cards, and so on. SDBs with the same microprocessors can use the same set of CSP drivers.
%_WINCEROOT%\Public\Common\OAK\Drivers These common drivers for non-native peripherals. Non-native peripherals are devices that exist on a plug-in card, or are embedded in an end-user product. This is platform independent code that links with the platform dependent code to create a driver. Common drivers are not specific to a given platform or microprocessor. Any SDB can use common drivers.
