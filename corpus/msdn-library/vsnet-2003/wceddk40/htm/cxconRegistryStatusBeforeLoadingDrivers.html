Registry Status Before Driver Loading

When Device.exe is loaded, it examines the HKEY_LOCAL_MACHINE\Drivers key for the RootKey value. It then examines the key pointed to by RootKey, in this case Drivers, for a DLL to load. In this example, it is the Registry Enumerator (RegEnum.dll). The Registry Enumerator's entry point, Init, is called with the HKEY_LOCAL_MACHINE\Drivers key. The Registry Enumerator examines the first level of keys just below the key passed to it according to Order. In this example, the Drivers\Debug key has Order of 0, so it is examined first.

The DLL loaded for Drivers\Debug is again the Registry Enumerator; it is re-entrant. The Flags value is set to 0x0001, or DEVFLAGS_UNLOAD, meaning that RegEnum.dll is unloaded, or its reference count is decremented. Its reference count is decremented in this example. Init is called with the Drivers\Debug key. It examines the immediate subkeys for ordering information. In this example, Drivers\Debug\EDBG has the lowest and only Order key. The Flags value for Drivers\Debug\EDBG is 0x0004, or DEVFLAGS_LOAD, which indicates that the DLL is not loaded because the Ethernet debugging adapter driver has already been loaded by the OAL. Any resources used by this device and any other devices not loaded by a bus driver should be excluded from the list of available resources used by the I/O Resource Manager.

The next key under the Drivers key is Drivers\Virtual with Order equal to 1. The Registry Enumerator is activated through a call to its Init function with the parameter Drivers\Virtual. Init examines the immediate subkeys for ordering information. In this example, Drivers\Virtual\NDIS has the lowest and only Order key. The Dll value is examined and NDIS.dll is loaded. The entry point, NDS_Init, is called with driver's Active key due the properties of the stream interface, which contains a Key value equal to Drivers\Virtual\NDIS. There are no more keys under Drivers\Virtual, so the Registry Enumerator's Init function returns.

The next key under the Drivers key is Drivers\CSP with Order equal to 2. The Registry Enumerator is activated through a call to Init with parameter Drivers\CSP. Init scans the registry for subkeys of Drivers\CSP. In this case, the first and only key is Drivers\CSP\Serial. The indicated DLL, Com16550.dll, is loaded and the entry point, COM_Init is called with the Active key, which contains a Key value of Drivers\CSP\Serial. The Unimodem subkey will be available to the serial driver.

The next key under the Drivers key is Drivers\ISA with Order equal to 3. The Registry Enumerator is used in place of an ISA bus driver. You can also use a Plug and Play ISA bus driver. If you do not use a Plug and Play ISA bus driver to configure and allocate ISA resources, the ISA resources must be allocated through the registry. In this case, RegEnum.dll can be used again to enumerate the registry for ISA devices. The use of the ISA subkey, as well as the CSP subkey, is optional. You can choose any registry structure, including hierarchical. For example, ISA can be a subkey of PCI, which can be a subkey of BuiltIn.

In this example, the first key by Order under Drivers\ISA is Drivers\ISA\Serial. The DLL is loaded. In this case, because Com16550.dll is already loaded from a previous key, nothing happens other than a reference count increment, and the default entry point is called. The next key by Order is Drivers\ISA\PCMCIA.

The last key by Order under the Drivers key is Drivers\PCI. The DLL is PCIbus.dll, a PCI bus driver and enumerator. This driver takes care of configuring and enumerating the PCI bus, allocating resources to the devices it finds on the bus, and populating the registry with device instances. It does this in conjunction with the I/O Resource Manager. When the PCI bus driver's Init function is called, it examines the values under Drivers\PCI for information regarding the resources available for use by the PCI bus. These values include MemBase and MemLen, which specify the ranges of memory-mapped I/O, and IoBase and IoLen, which specify the ranges of port I/O.

Device Identification

After configuring the PCI bus, the PCI bus driver re-scans the PCI bus for the purpose of enumeration and matching devices with registry entries. When a device is enumerated, the registry is searched using the device's identifiers. The following table shows the device identifiers.

Subkey Description
Class Identifies basic function of device, for example, a mass storage controller.
SubClass Identifies a specific sub-class of basic function, for example, an IDE controller.
ProgIF Identifies a register-specific programming interface, for example, USB OHCI versus UHCI.
VendorID Identifies the manufacturer of the device.
DeviceID Identifies the type of device.
SubsystemVendorID Identifies the vendor of a card or subsystem that uses a device.
SubsystemID Identifies the type of card or subsystem that uses a device.
RevisionID Identifies the revision number of the device.

The identifiers are listed in order of increasing specificity. When matching a found device with a registry entry, all of the values that are listed in the registry must match the found device. For example, a driver that works with all 16550-compatible serial controllers has the values shown in the following table.

Subkey Value Description
Class 7 Simple communications controllers
SubClass 0 Serial
ProgIF 2 16550-compatible serial controller
Note   These values are part of the PCI Revision 2.2 Specification.

If a particular serial driver were tailored to a particular vendor's device, then the VendorID and DeviceID values would be listed as well. The registry entry for this driver would only match a device that contains the exact same Class, SubClass, ProgIF, VendorID and DeviceID. The VendorID, DeviceID, SubsystemVendorID, SubsystemID and RevisionID can have a list of values associated so the driver can be matched with a subset of cards.
