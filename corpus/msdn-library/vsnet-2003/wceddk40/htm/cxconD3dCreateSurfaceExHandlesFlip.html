D3dCreateSurfaceEx Handles and Flip

DirectDraw's surface structures are designed to represent conceptual surfaces, not necessarily specific locations in video memory. The main usage of this abstraction is in a primary flipping chain, where the application uses one constant surface object to represent the back buffer, even though the back buffer may be moving around in video memory as a result of the Flip operation.

The Flip method takes a ring of surfaces, and rotates (sequentially reassigns) their video memory pointers around this ring. In the particular case of two surface objects, the process is reduced to trading their video memory pointers. In addition, the DirectDraw run time also rotates the D3dCreateSurfaceEx handles associated with each surface, and the driver-owned contents of the dwReserved1 members of each surface. This behavior has some interesting consequences for a driver, and effectively rules out the embedding of pointers to DirectDraw's surface structures inside the driver's own surface structures.

Consider two surface objects A and B that have associated handles HA and HB, and fpVidMem (a member of the DDRAWI_DDRAWSURFACE_GBL structure) values of FA and FB. Further, suppose that the application is using surface structure A to refer to the back buffer of a flipping chain. At Flip time, the handles and both fpVidmem values are swapped, so that surface A has HB and FB, and surface B has HA and FA. The application now tries to draw to the back buffer, surface A, which should represent the video memory at FB (because the application called Flip).

A drawing command is issued to the driver, which looks up the handle associated with that surface (which is now HB, not HA). What would happen if the driver merely stored a pointer to the DirectDraw surface structure? The driver would look up HB, then follow the stored pointer to surface B, which now has an fpVidMem value of FA. Drawing would begin on the video memory at FA. This is not what the application is expecting. If, on the other hand, the driver were to store surface data in its own structures, rather than following a pointer to DirectDraw's surface structure, then HB would still resolve to FB, and drawing would occur on the correct surface. This latter case is the way the current DDI is implemented.
