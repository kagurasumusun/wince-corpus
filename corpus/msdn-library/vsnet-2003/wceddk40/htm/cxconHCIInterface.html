Host Controller Interface

The host controller interface (HCI) provides a uniform interface method for accessing Bluetooth hardware capabilities.

During the initialization sequence, the HCI creates read and write threads, establishes a connection to the Bluetooth transport, and performs a reset and read of device buffer sizes. It then enters an initialized state and is ready to accept clients.

Clients connect to HCI using the HCI_EstablishDeviceContext function.

HCI events, unlike with the other layers of the stack, are sometimes caused by executing commands. For example, issuing CreateCommand to the Bluetooth controller causes a CommandStatus event. This event notifies the stack that a command has been accepted for execution. When the connection is established or rejected, a ConnectionComplete event is issued. Some events, such as ConnectionComplete, occur only as a result of an executed command. Some events, like LinkKeyChanged, occur as a result of an executed command or an act of the peer device, without the command issued. Other events, like ConnectionRequest, occur only as a result of an action of a peer Bluetooth device.

The HCI layer matches events to commands currently in execution and returns a call context for the executing command (and retire the command) only when a corresponding event has signaled.

In general, HCI commands are divided into two non-intersecting sets: those that are executed immediately by the card and are completed by controller issuing a CommandComplete event, and those that require remote action and depend on the wireless media. These are signaled for acceptance by the controller sending the CommandStatus event, and are completed by one of the Bluetooth events.

Therefore, the callback table in the HCI can be loosely subdivided into commands that carry meaningful output values and commands that carry only status. The following example code shows a command that carry meaningful output values.

typedef int (*HCI_ReadPINType_Out)(
void          *pCallContext,
unsigned char  status,
unsigned char  PIN_type
);

Some write commands that have immediate effects, and are thus completed with CommandComplete, fall under the category of commands that carry only status. The following example code shows a command that carry only status.

typedef int (*HCI_Inquiry_Out) (
void          *pCallContext,
unsigned char  status
);

All events in the HCI event table carry both user context and call context. The following example code shows this.

typedef int (*HCI_InquiryCompleteEvent) (
void          *pUserContext,
void          *pCallContext,
unsigned char  status,
unsigned char  num_responses
);

When an event is generated by a command, the command is retired at this point and pCallContext is non-NULL. If the event comes asynchronously, pCallContext is NULL.

The HCI can be used to issue a hardware-dependent command by using the following facility.

#define BTH_MARKER_NONE            0
#define BTH_MARKER_CONNECTION      1
#define BTH_MARKER_ADDRESS         2

typedef struct _packet_marker {
   unsigned int      fMarker;
   union {
      BD_ADDR         ba;
      unsigned short   connection_handle;
   };
} PacketMarker;

typedef int (*HCI_CustomCode_In) (
HANDLE           hDeviceContext,
void            *pCallContext,
unsigned short   usOpCode,
unsigned short   cPacketSize,
unsigned char   *pPacket,
PacketMarker    *pMarker,
unsigned char    cEvent
);

The PacketMarker structure is used do a select command if it is differentiated by some of its parameters. For example, there can be five CreateConnection commands outstanding, each to a different Bluetooth device. The PacketMarker for every one will then contain a BTH_MARKER_ADDRESS and ba, the address of the target device.

Use this function with caution, because issuing commands through a command-specific interface can have a side effect not created by a CustomCode command.

The HCI_INTERFACE contains one entry point for each HCI-level Bluetooth command as defined by the HCI Specification of the Bluetooth Core Specification.

Commands that terminate with a CommandComplete event have return parameters indicated by _Out functions in HCI_CALLBACKS. Commands that terminate with a CommandStatus event will have a boilerplate completion routine that only has status. If the status is success, the command will really terminate when an appropriate event is issued.

Not all HCI commands are implemented. These that are not are stubbed with NULL pointers in HCI_INTERFACE. The list of unimplemented commands shrinks daily and therefore cannot be part of this guide.
