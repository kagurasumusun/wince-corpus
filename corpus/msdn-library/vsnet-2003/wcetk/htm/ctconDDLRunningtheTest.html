Running the Test

The following command line shows the syntax for running a test using Ddlx.dll.

tux –d ddlx –c "-d test_dll –i device_index -c parameters"

The -d ddlx –c parameters outside of the quotation marks are parameters for Tux. These parameters instruct Tux to load Ddlx.dll into the process space for Tux and then pass the entire string enclosed in quotation marks to Ddlx.dll.

The list of parameters for Ddlx.dll, enclosed in quotation marks, does not require a space, a command-line option, and its argument. However, you must insert a space between each command-line option. The following command line is not acceptable.

tux -d ddlx -c "-dtest.dll-i2"

The following table shows the parameters for DDLX.

Parameter Description
-d test_dll File to register. If you do not specify this option, DDLX attempts to load Generic.dll.
-i device_index Device index for the driver. If you do not specify this option, DDLX uses a value of 1.
-c parameters Additional parameters for test_dll to pass on to the device driver being tested.

The following command line shows the syntax for a sample test.

tux –o –d ddlx –c "-d test.dll –i 2 –c 1 2 3"

In this example, the device driver being tested receives the "1 2 3" string as a command line.

If you do not need to specify a device index or any additional command line parameters, you can omit the quotation marks and the –d parameter. The following command line shows the syntax for this scenario.

tux –o –d ddlx –c test.dll

The general guidelines for writing test procedures are the same for Tux and DDLX as they are for Tux alone. Test procedures create the function table, process ShellProc commands, process TestProc commands, and so on. However, in the context of a .mak file, there are the following two differences between a typical Tux test procedure and a Tux and DDLX test procedure:

  • Ddlxioct.lib must be linked with your test procedure as a source library, not as a target library.
  • Your .def file needs to include all required device driver entry points.

Your test must accept DeviceIoControl commands because it runs as a device driver. However, no additional coding is required in your test procedure because Ddlxioct.lib handles the processing of these commands by receiving them and passing them along to your test procedure as standard Tux messages.

Note   Ddlxioct.lib does not implement any test procedures. It returns only a passing value to satisfy Device.exe.

Ddlxioct.lib also exposes a function to control debugger output. The DDLXDebuggerControl function accepts a DWORD containing flags set for debugger output, and returns a DWORD indicating the previous state of the output of the debugger. To use this function, you must include Ddlx.h. For more information, see the Ddlx.h file.

The following code example shows a typical .mak file.

TARGETNAME=ddlxtest
TARGETTYPE=DYNLINK
TARGETLIBS=\
   $(_COMMONSDKROOT)\lib\$(_CPUINDPATH)\coredll.lib \
   $(_PROJECTOAKROOT)\lib\$(_CPUINDPATH)\kato.lib
DLLENTRY=DllMain
INCLUDES=\
   $(_PUBLICROOT)\common\oak\inc
SOURCES=shelproc.cpp \
   testproc.cpp \
   globals.cpp
SOURCELIBS=\
   $(_PROJECTOAKROOT)\lib\$(_CPUINDPATH)\ddlxioct.lib

The following code example shows a typical .def file.

EXPORTS
   ShellProc
   gen_Init
   gen_Deinit
   gen_Open
   gen_Close
   gen_Read
   gen_Write
   gen_Seek
   gen_IOControl
   gen_PowerUp
   gen_PowerDown
