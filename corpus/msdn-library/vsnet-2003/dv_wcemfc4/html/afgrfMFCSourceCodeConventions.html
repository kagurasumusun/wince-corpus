MFC Source Code Conventions

MFC supplies full source code, including

  • Header files (.h) in the MFC\Include directory
  • Implementation files (.cpp) in the MFC\Src directory

The following paragraphs review MFC conventions for inserting comments in various parts of each class, what these comments mean, and what to expect in each section. ClassWizard and AppWizard in the eMbedded Visual C++ IDE use similar conventions for the classes they create. You will probably find these conventions useful for your own code.

Public, protected, and private C++ keywords

In MFC header files, each class may have several of these. For example, public member variables and functions might be under more than one public keyword. This is because MFC separates member variables and functions based on their use, not by the type of access allowed. MFC uses private sparingly; even items considered implementation details are generally protected and many times are public. Although access to the implementation details is discouraged, you make this decision.

Comments

In the MFC source files and the files that AppWizard creates, comments like these within class declarations appear in this order:

  • // Construction
  • // Attributes
  • // Operations
  • // Overridables
  • // Implementation

An Example of the Comments

The following partial listing of class CStdioFile uses most of the standard comments that MFC employs in its classes to divide class members by the ways they are used:

class CStdioFile : public CFile
{
    DECLARE_DYNAMIC(CStdioFile)

public:
// Construction
    CStdioFile();
...

// Attributes
    FILE* m_pStream;    // stdio FILE
...

// Operations
    virtual void WriteString(LPCTSTR lpsz);
...
    virtual LPTSTR ReadString(LPTSTR lpsz, UINT nMax);
...

// Implementation
public:
...
};

These comments consistently mark sections of the class declaration that contain similar class members. These are MFC conventions, not set rules.

The // Construction Comment

The // Construction section of an MFC class declaration declares constructors, in the C++ sense, as well as any initialization functions required to use the object. For example, CWnd::Create is in the construction section because, before you use the CWnd object, it must be fully constructed by first calling the C++ constructor and then calling the Create function. Typically, these members are public.

The // Attributes Comment

The // Attributes section of an MFC class declaration contains the public attributes or properties of the object. Typically, these are member variables, or Get/Set functions. The Get and Set functions may or may not be virtual. The Get functions are usually const, because in most cases they do not have side effects. These members are normally public; protected and private attributes are typically found in the implementation section.

In the sample listing (above) from class CStdioFile, the list includes one member variable, m_pStream. Class CDC lists nearly 20 members under this comment.

Large classes, such as CDC and CWnd, may have so many members that listing all attributes in one group does not add clarity. In such cases, the class library uses other comments as headings to delineate the members. For example, CDC uses // Device-Context Functions, // Drawing Tool Functions, // Drawing Attribute Functions, and so on. Groups that represent attributes follow the usual syntax described above. Many OLE classes have an implementation section called // Interface Maps.

The // Operations Comment

The // Operations section of an MFC class declaration contains member functions that you can call on the object to make it perform operations. These functions are typically non-const since they usually have side effects. They may be virtual or nonvirtual, depending on the needs of the class. Typically, these members are public.

In the sample listing from class CStdioFile (above), the list includes two member functions under this comment: ReadString and WriteString.

As with attributes, operations may be further subdivided.

The // Overridables Comment

The // Overridables section of an MFC class declaration contains virtual functions that you can override in a derived class when you need to modify the base class behavior. They are usually named starting with On, although this is not necessary. Functions here are designed to be overridden, and often implement or provide some sort of callback or hook. Typically, these members are protected.

In MFC itself, pure virtual functions are always placed in this section. A pure virtual function in C++ is one of the form:

virtual void OnDraw( ) = 0;

In the sample listing from class CStdioFile above, the list includes no overridables section. Class CDocument, on the other hand, lists approximately 10 overridable member functions.

In some classes, you may see the comment // Advanced Overridables. Only advanced programmers should attempt to override these functions.

The conventions described in this topic also work well, in general, for Automation (OLE Automation) methods and properties. Automation methods are similar to MFC operations. Automation properties are similar to MFC attributes. Automation events, supported for ActiveX (OLE) controls, are similar to MFC overridable member functions.

The // Implementation Comment

The // Implementation section is the most important part of any MFC class declaration.

This section houses all implementation details. Member variables and member functions can appear in this section. In addition, members declared below the implementation line are not documented, although some implementation is discussed in technical notes. Overrides of virtual functions in the base class reside in this section, regardless of which section the base class function is defined in, because the fact that a function overrides the base class implementation is considered an implementation detail. Typically, these members are protected, but not always.

Members declared below // Implementation may be declared as public, protected, or private. Use these members with caution, because they might change in the future. Declaring a group of members as public may be necessary for the class library implementation to work correctly. However, this does not mean that you may safely use the members so declared.

You may find comments of the remaining types above or below the // Implementation comment. In either case, they describe the kinds of members declared below them. If they occur below // Implementation , you should assume that the members might change in future versions of MFC.

Viewing the Browse Information File

You can look through MFC source code for debugging purposes or to get a better idea of what's going on behind the scenes by using the Source Browser (available from the Tools menu) to view the Browse Information File. If a class or symbol is not included in this file, use the Find In Files command on the File menu as an alternative technique.
