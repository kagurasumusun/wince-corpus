Porting Applications to Windows CE .NET

Code reuse is a common goal in software development. The issues that follow are among those that might affect reusing code written for platforms other than your current target platform.

Besides code issues as such, UI design and style issues often dictate changes when moving from one platform to another. For example, menu or command bars on one device may follow a style that is different from those on another. Be sure to read the documentation in the target platform SDK for guidance in this area.

Typical portability scenarios and considerations include the following:

Porting Code from a Desktop Application

An application designed for the desktop is not usually appropriate as a portable application. Typically, only a subset of the features of a desktop application is necessary (or even desirable) in a mobile device. In this case you can choose the functions of the desktop application that would be useful to a small device user and create a portable application. You can make this application work as a portable companion to the desktop application.

Porting Code Written In Earlier Versions Of MFC For Windows CE

For the most part, it is a simple process to use MFC for Windows CE .NET to compile applications created with previous versions. However, you may need to make a few minor adjustments to guarantee compatibility.

For example, versions 1.0 and 2.0 of MFC for Windows CE automatically create command bars whenever they create frame windows. You should eliminate these command bars to ensure that your application is compatible with MFC for Windows CE 3.0 or later. You can create your own command bars using the CCeCommandBar class, either manually or with the help of one of the MFC application wizards.

Another possible backward compatibility issue concerns the CWinApp constructor. The CWinApp constructor in MFC for Windows CE 3.0 and later takes one optional parameter, whereas in versions 2.0 and earlier CWinApp allowed up to two optional parameters. To avoid compiler errors due to this difference, simply rewrite your calls to the CWinApp constructor so that they use a single optional parameter. For more information, see CWinApp topics in the reference section.

In addition, version 2.0 of MFC for Windows CE automatically painted the client area before processing an application’s OnNewDocument handler. Versions of MFC for Windows CE after 2.0 perform no painting before the application calls either the OnNewDocument handler or the AfxMsgBox function. If your application engages in extensive processing before calling the OnNewDocument handler and you want to avoid a blank screen, call UpdateWindow.

Windows CE 3.0 is no longer a supported target in eMbedded Visual C++ 4.0. No platforms will be available to you when you open a project that targets a Windows CE 3.0 or earlier platform in eMbedded Visual C++ 4.0 To port code that targets devices on these platforms, open a new project that targets the desired platform, and add files from the old project to the new one.

Finally, earlier versions of Windows CE did not check registry settings that controlled a COM object's threading model. Though the apartment threading model was unsupported, COM objects, except DCOM objects, could specify any threading model, including apartment, and still run successfully. Because Windows CE .NET always checks the threading model, you must make sure that your COM objects specify and use either the free threading model or the both threading model.
