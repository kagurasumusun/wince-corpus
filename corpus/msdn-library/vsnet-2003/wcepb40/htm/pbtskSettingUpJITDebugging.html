JIT Debugging Setup

In order to use JIT debugging, you must first configure your platform to support KITL services, and package the correct debugging libraries into the OS kernel. To find more about configuring your platform for KITL, see Configuring KITL Services.

The second prerequisite to JIT debugging is that the developer needs to enable debugger support in the kernel. There are two possibilities for how this can be accomplished:

  • The first possibility is that the static library file KdStub was included in the kernel at build time; for example, Nk.exe contains KdStub.
  • The second possibility occurs when the device's kernel does not contain KdStub; in this situation, the option is to dynamically load KdStub. To do this, the OS developer must run Loaddbg.exe, which will add the dynamically linked library Dbg.dll.

The first possibility is typical for a debug version of an OS, during the early phase of platform development. During the final phase, the OS developer will be working with a release build; the second option mentioned previously provides JIT debugging for this phase. Instead of the debug build with KdStub, the developer creates a release build of the OS, and runs Loaddbg.exe. This loads Dbg.dll, which acts as KdStub for the release build.

This dynamically linked library must be loaded beforehand. If it is not loaded, then the exceptions will not be handled in the way described earlier, and unhandled second-chance exceptions will simply cause the relevant application to be terminated. Therefore, in order to have the option of running the kernel debugger, the developer must run loaddbg.exe before testing a release build. In contrast, the final release of an OS should not contain these debug libraries. This ensures the proper response to a second-chance exception: the application terminates but the operating system stays functional.
