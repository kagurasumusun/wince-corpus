Cesh.exe Debugging Commands

Once Cesh.exe is running on the target device, you can enter Cesh.exe commands to transfer files to the target device and to debug applications. There are three ways to enter Cesh.exe commands.

  • If you use a command prompt window, enter commands at the Windows CE prompt.
  • If you use the Platform Builder IDE, choose CE Target Control… from the Target menu.

The following list shows the Cesh.exe commands.

?
Displays a list of commands.
break
Breaks into the Microsoft kernel debugger program.
dd Address Size
Dumps DWORDs.

The Address parameter specifies the beginning address for the dump. This value must be an hProc. The Size parameter specifies the size of the dump. You must specify a value for Size.

df Filename Address Size
Dumps DWORDs to a file for the specified process identifier.

The Filename parameter specifies the file into which the dump is saved. The Address parameter specifies the beginning address for the dump. This value must be an hProc. The Size parameter specifies the size of the dump.

dis
Discards all memory that can be discarded.
gi [proc | thrd | mod | delta | all]
Gets information on these processes: processes with their threads, modules, critical sections with threads waiting, and events.

The proc parameter lists all processes in the system. The thrd parameter lists all processes with their threads. The mod parameter lists all modules loaded. The delta parameter lists only those threads that have changes in CPU times. The all parameter lists all of the preceding parameters. If you do not supply a parameter, gi all, which is the default, is used.

The full parameter displays a set of tables showing the virtual memory usage for all the processes in the system. The table is made up of ASCII characters that represent what each virtual page is being used for. When you use this parameter, the summary information is detailed in a line-marked page summary. This parameter displays one table per process in the system. Each line in a table represents 64K of virtual memory within a process. The first hexadecimal number on each line indicates the base address of the virtual memory for each 64K chunk. The second number on each line, in parentheses, indicates the number of locked pages within the 64K chunk and can generally be ignored. When addresses are skipped within a table, it signifies that no pages are presently allocated in the entire 64K chunk. Following the first two numbers on a line is a series of ASCII characters, each representing a single page of memory within the line's 64K chunk.

The following table shows the memory information definitions that are included in the page summary.

Character Definition
<blank> A blank space indicates a virtual page that is not currently allocated. Does not require a physical page.
- Reserved but not in use. Indicates a virtual page that is currently allocated but not mapped to any physical memory. Does not require a physical page.
C Code pages in ROM. Does not require a physical page.
c Code pages in RAM. Requires a physical page.
S Indicates a virtual page that holds a stack. Requires a physical page.
P Peripheral memory (pages used to map device memory by using VirtualAlloc). Indicates a virtual page that is used to map a range of hardware addresses. Does not require a physical page. Peripheral memory may include frame buffer memory.
W Indicates a virtual page that holds read-write data. Requires a physical page. Read-write pages include global variables as well as dynamically allocated memory.
O Indicates a virtual page that is used by the object store. Requires a physical page. Should only appear in the Filesys process.
? Contents unknown.
r Read-only data pages in RAM. Requires a physical page. Read-only data primarily comes from data items that are declared as a const type in the source code.
R Read-only data pages in ROM. Does not require a physical page. Read-only data primarily comes from data items that are declared as a const type in the source code.
kp [ Pid | Pindex ]
Ends a process.

The Pid parameter specifies which process to end. The parameter is a process identifier, which is found in the hProcess column displayed by the gi command. You must enter this value as a hexadecimal number. The following code example shows the command that you must enter to end the process if hProcess is 2c57506a. 

kp 0x2c57506a

The Pindex parameter consists of the leftmost numbers, from 1 to n, of the process index. The index is displayed by the gi proc command.

s Processname
Starts the process.

The processname parameter refers to the name of the process.

run Processname
Runs a series of processes listed in a text file specified by the Processname parameter. You can use the run command to run several processes or executable files, one process or executable file at a time.
Note   If you use the run command, the Threads, Processes, and Modules and Symbols windows will not respond until the processes have completed. Additionally, the Windows CE prompt will not be available at the command line during this time.

zo [p | m] [Index | Name] [Zone, [on | off][ZoneIndex]]
Performs debugging zone operations.

The p parameter specifies per-process operations; the m parameter specifies per-module operations.

The Index parameter specifies the index of the process or module, as returned by the gi command. If no further parameters are specified, this command returns the current settings with the zone names.

The Name parameter specifies the name of the process or module. If no further parameters are specified, this command returns the current settings with the zone names.

The Zone parameter specifies the zone to which this process or module zone is set. Any hexadecimal values must be preceded with 0x.

The on and off parameters specify whether to set the bits of the current zone mask on or off.

Examples

The following code example shows how to start Reversi.exe. 

s reversi

The following code example shows how to display information about running processes. 

gi proc

The following code example shows how to display the zone names for the process at index 2.

zo p 2

The following code example shows how to set the zone for the module at index 0 to 0x100. 

zo m 0 0x100

The following code example shows how to set bits 3 and 5 on and bit 2 off for process 3. 

zo p 3 on 3,5 off 2

Remarks

When a process loads a DLL, virtual pages are allocated within the process address space to map to the DLL. If multiple processes map to the same DLL, each process will have virtual memory allocated to it to map to the DLL, even though each process shares the same physical page. Each process in the system exists in a 32M chunk of virtual space; within this space, a DLL will always be loaded in the upper 16M of memory. Thus, when looking at the output of mi full, any virtual page that is allocated in the upper 16M of a process virtual space can be attributed to a DLL that the process is using. By using the gi mod command, you can obtain a list of DLLs currently loaded in the system and their base addresses within the system. By using this base address and a process's base address, you can then determine which DLL is using which page within a process virtual space. Within the table for a particular process, pages in which the second nibble of the address is odd are attributable to a DLL that is being mapped in. For example, 0x0f000144 is an address mapped to a DLL, whereas 0x0e000144 is not.

To determine which DLL is mapped to a particular address in a process

  1. Subtract the process base address from the address of interest.

    The process base address is shown within the output of mi full as the slot base.

  2. Use the gi mod command to obtain the address of all modules loaded in the system and view the dwVMBase column.
  3. View the output of gi mod for a module that covers the address you calculated in step 1.

    To determine what DLL is using the page at 0x9db00000 within Device.exe, subtract the process base address from the address of interest. According to the examples that follow, you would use these addresses: 

    0x09db0000 - 0x08000000 = 0x01db0000

    The following example is a truncated version of the table output using mi full for the device.exe process. 

    Memory usage for Process 80209c74: 'device.exe' pid 3
    Slot base 08000000  Section ptr 817d5000
    09d90000(0): -CCCCCWr-
    09db0000(0): -CCCCCW-R-
    09dc0000(0): -CCCCCWrR-

    The following example is a truncated version of the output of the gi mod command: 

    MOD: Name            pModule :dwInUSE :dwVMBase:CurZone
M00: unimodem.dll    816a9d08 00000008 01db0000 00000000
M01: TAPI.DLL        8173f000 00000008 01dc0000 00000000
M02: IR.DLL          8173f290 00000020 01cd0000 00000000
M03: keybddr.dll     8173f468 00000020 01d30000 00000000
  4. Look up the resulting address in the dwVMBase column of the gi mod output.

    In the previous example, Unimodem.dll is the user of the page.
