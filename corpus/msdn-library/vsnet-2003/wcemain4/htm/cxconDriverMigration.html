Driver Migration

A device driver from Windows CE version 3.0 is source code compatible with Windows CE .NET This allows a driver to be recompiled and used on Windows CE .NET without any changes to its sources or configuration files. However, due to the many changes in the build system in Windows CE .NET, you may have to change a few build or linker parameters to correctly build your driver.

Binary compatibility of device drivers from Windows CE 3.0 is not tested or guaranteed. However, in general, a Windows CE 3.0 device driver binary is expected to work correctly on a Windows CE .NET-based platform. Device drivers are expected to read their SYSINTR value from the registry. Using IOCTL_HAL_TRANSLATE_IRQ may not provide a one-to-one IRQ to SYSINTR mapping, which would require the use of an installable ISR. If your Windows CE 3.0 device driver uses IOCTL_HAL_TRANSLATE_IRQ, you will need to modify it to read its SYSINTR value from the registry.

Aside from the source or binary compatibility, you should consider migrating or transitioning your device drivers to Windows CE .NET to take advantage the improvements. The following topics related to driver migration provide lists of issues you should consider when migrating a device driver to Windows CE .NET:

Migration issue Description
CSP and common drivers Windows CE .NET provides the basic infrastructure to rapidly create a BSP by reusing many device drivers from a number of driver libraries. These libraries include the following:
  • CPU Support Package or CSP drivers for microprocessor-native peripherals and microprocessor-specific OAL functions. These drivers are in %_WINCEROOT%\Public\Common\Oak\Csp.
  • Common drivers for peripherals not integrated into the microprocessor, such as Ethernet, display, audio, storage, USB class devices, and so on. These drivers are in %_WINCEROOT%\Public\Common\Oak\Drivers and %_WINCEROOT%\Platform\%_TGTPLAT%\Drivers.

When developing a BSP, you should use these device drivers in your BSP where applicable. This minimizes the amount of new source code that you have to write while developing a BSP. When writing a device driver for your peripherals, you should model your driver on one of the sample drivers.

For more information, see Creating a BSP.

Device driver loading model The device driver loading model provides a consistent loading architecture for all drivers. You should update your drivers to load under the new model. The following list describes the new loading process for devices:
  • During platform boot up, the Device Manager loads the Registry Enumerator (RegEnum.dll). For more information about the Device Manager, see Device Manager.
  • The Registry Enumerator enumerates the registry, load drivers for all built-in devices, and all bus drivers it recognizes on the system. For more information about the Registry Enumerator, see Registry Enumerator.
  • Bus drivers are subsequently responsible for loading drivers for the devices on their buses. For example, the PCMCIA host controller driver will load drivers for all PC Card client drivers.

Device specific information such as PCMCIA resides in the appropriate bus driver, not in the Device Manager. This means that the PCMCIA bus driver should load PC Card client drivers, so update the registry entries accordingly.

For more information, see Device Driver Loading Model.
NDIS driver loading model To load NDIS miniports, use the new NDIS Driver Loading Model. See NDIS Driver Implementation Guide for more information.
ActivateDeviceEx Use ActivateDeviceEx to load all your device drivers. You can use ActivateDevice, but it simply calls ActivateDeviceEx. Do not use RegisterDevice to load drivers.
I/O Resource Manager Use the I/O Resource Manager to request resources. When the system boots, the Registry Enumerator enumerates the registry as setup by the OEM or the BSP developer and loads all the built-in devices based on this registry information. At this time, the I/O Resource Manager will then track the current state of resources available in the system and then manage all further I/O resource requests and allocations by bus drivers. This means that all bus drivers should request I/O resources from the I/O Resource Manager when they load a client driver for installable or other types of devices.

For more information, see I/O Resource Manager.
PCI bus driver The PCI bus enumerator or the PCI bus driver removes unnecessary PCI specific code from the OAL and device drivers. Use the registry information provided by the PCI bus driver instead of using driver code that scans the PCI bus to read bus address registers and interrupt information from the PCI configuration space header. See PCI Device Support for details on what PCI code the OAL requires, especially if the debug device is on the PCI bus.

To allow PCI enumeration of all PCI devices, update the registry for your platform. See the ARM Integrator BSP in %_WINCEROOT%\Platform\ARMIntegrator\Files for an example implementation.
Installable ISRs Installable ISRs allow multiple devices to share interrupts. They also extend the ability to process the device in the ISR in addition to the IST. You can program an installable ISR in a language other than assembly. You should update the ISRs for your device driver if you want to allow interrupt sharing. If you need an installable ISR, you can use the Generic Installable ISR (GIISR.dll) sample approximately 90% of the time, provided in the ISR, you only need to recognize the device generating the interrupt.

For more information, see Installable ISRs, Installable ISRs with Drivers, and Shared Interrupts.
Power management Implementing peripheral-level power management in your device drivers provides a great deal of flexibility to OEMs in controlling and managing the overall system level power requirements of an OEM device. You should update your device drivers to be managed by the Power Manager by following these recommendations:
  • Implement the Windows CE stream interface in your driver.
  • Support as many device power states as possible in your driver to support overall power management.

For more information, see Power Management.
Device interface notifications A new device interface notification mechanism allows a device driver to send notifications to applications, services, and any other module in the system on the arrival or removal of a device interface. This is the equivalent of Plug and Play functionality. You should update your drivers to advertise their interface and send device notifications to the system.

For more information, see Device Interface Notifications.
Audio Driver Migration Windows CE 3.0 waveform audio drivers should migrate to Windows CE .NET with no modifications. However, new Microsoft DirectSound® and audio mixer extensions are available.

Support for DirectSound hardware abstraction layer (HAL) drivers has been discontinued in Windows CE .NET. The DirectSound driver functionality is now handled by the DirectSound extensions that are part of the Unified Audio Model.

For more information, see Audio Drivers and the Ensoniq sample driver source code. The sample code is in the %_WINCEROOT%\Public\Common\Oak\Drivers\Wavedev\Unified\Ensoniq directory.
Device Driver Threads Windows CE .NET sets the environment variable IMGNOTALLKMODE=1. Therefore, your code should not assume that driver threads run in kernel mode. When your driver must access restricted space, include code similar to the following. 
oldmode = SetKMode(TRUE);
DoSomething();
SetKMode(oldmode);
