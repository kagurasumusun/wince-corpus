Update your OAL

The following changes should be made in the OAL for your BSP:

  1. Implement a variable system timer tick in the OAL.

    This allows for better power management on your BSP. Many of the sample BSPs implement a variable system timer tick. Use them as examples. The variable system timer tick function is implemented in your OAL.

  2. Update IRQ-to-SYSINTR mappings.

    The PCI bus driver requires the ability to obtain and manage the translations for SYSINTR and IRQ values. The following table shows the functions to implement for the PCI bus driver to work. These functions are exposed through the HAL IOCTLs described in the next step.

    Function Description
    OEMTranslateIrq Takes an IRQ value and returns a logical interrupt, SYSINTR, value. If the IRQ maps to more than one SYSINTR, the first mapping will be returned.
    OEMTranslateSysIntr Takes a logical interrupt, SYSINTR, value and returns the corresponding IRQ.
    OEMRequestSysIntr This is for new SYSINTR mappings. Requests a new logical interrupt, SYSINTR, value for the specified IRQ. This sets up a new mapping in the OAL.
    OEMGetInterrupt Requests an IRQ value for the device location specified.
  3. Add the following HAL IOCTLs. They are added to Windows CE.
    • IOCTL_PROCESSOR_INFORMATION, this provides information on the processor such as the core, name, vendor, and so on.
    • IOCTL_HAL_TRANSLATE_IRQ, this calls OEMTranslateIrq for x86-based OALs, or OEMRequestSysIntr for OALs not based on x86. This IOCTL is implemented for backwards compatibility only. It may be removed in future releases. IOCTL_HAL_REQUEST_SYSINTR should be used instead.
    • IOCTL_HAL_REQUEST_SYSINTR, this calls OEMRequestSysIntr. Only bus drivers should use this IOCTL to request SYSINTRs for their client drivers. Built-in drivers should rely on the OAL to setup an initial IRQ to SYSINTR mapping. In all cases, drivers should read their SYSINTRs from the registry.
    • IOCTL_HAL_REQUEST_IRQ, this calls OEMGetInterrupt. Returns an interrupt number for a device based on its bus location. Currently, only the PCI bus is supported.
    • IOCTL_HAL_INITREGISTRY, this IOCTL is called by the file system before the registry is generally available to allow the OAL to pre-populate the registry with information about debugging devices such as devices used by KITL.
    • IOCTL_KITL_GET_INFO
    • IOCTL_VBRIDGE_GET_TX_PACKET, this is used by VMINI.
    • IOCTL_VBRIDGE_GET_TX_PACKET_COMPLETE
    • IOCTL_VBRIDGE_GET_RX_PACKET
    • IOCTL_VBRIDGE_GET_RX_PACKET_COMPLETE
    • IOCTL_VBRIDGE_GET_ETHERNET_MAC
    • IOCTL_VBRIDGE_CURRENT_PACKET_FILTER
    • IOCTL_VBRIDGE_802_3_MULTICAST_LIST
    • IOCTL_VBRIDGE_WILD_CARD
    • IOCTL_VBRIDGE_SHARED_ETHERNET
    • IOCTL_HAL_ENABLE_WAKE, this is used to determine which logical interrupt, SYSINTR, value can be used to bring a platform out of suspend.
    • IOCTL_HAL_DISABLE_WAKE
    • IOCTL_HAL_POSTINIT, this is called after OEMInit and provides a context to perform additional platform initialization.
  4. Remove the following IOCTLs. They are removed from Windows CE, so you should remove them from your OAL.
    • IOCTL_EDBG_REGISTER_CLIENT
    • IOCTL_EDBG_DEREGISTER_CLIENT
    • IOCTL_EDBG_REGISTER_DFLT_CLIENT
    • IOCTL_EDBG_SEND
    • IOCTL_EDBG_RECV
    • IOCTL_EDBG_SET_DEBUG
    • IOCTL_HAL_PROFILE
    • IOCTL_COLLECTOR_REGISTER
    • IOCTL_COLLECTOR_SEND
    • IOCTL_COLLECTOR_UNREGISTER
  5. Remove CreateStaticMapping space.
  6. Enable KITL in the BSP. Perform the following to enable KITL in your BSP or to migrate from EDBG to KITL:
    • Use Halkitl.c from a similar platform. Configure function callback pointers to use the EDBG driver for your platform.
    • In your OAL, you should only enumerate KITL devices and any special debug or other devices that need to be set up by the OAL. After enumerating these devices, use the PCIReg function call in conjunction with IOCTL_HAL_INITREGISTRY and populate the registry with information on the KITL and other debug devices.
    • Call KitlInit or InitDebugEther, which calls KitlInit, this depends on the Halkitl.c version used.
  7. Enable Installable ISRs. Perform the following steps:
    • Your ISRs should call NKCallIntChain on interrupts you want shared and interrupts you want to support installable ISRs on.
  8. Set up and initialize built-in devices.

    You should populate the registry with the correct I/O resources information for all the built-in and debug devices on the hardware platform. When the system boots, the Registry Enumerator will enumerate the registry and load all the built-in devices. I/O resource information includes memory windows such as MemBase and MemLen, I/O windows such as IoBase and IoLen, interrupt number (Irq) and SYSINTR (SysIntr). The initial state of the I/O Resource Manager is set in the registry. The initial state should indicate that resources used by the built-in devices are already in use. The I/O Resource Manager will track the current resources available in the system and then manage all further I/O resource request and allocations by bus drivers.

  9. Add a Hive-Based Registry.

    If your hardware platform has persistent storage and it supports suspend without memory refresh, then you should use a hive-based registry. You need to replace the Object Store Based Registry with the hive-based registry in your BSP, adjust the configuration registry keys in your Platform.reg file, and implement a registry flushing strategy.

  10. Support KITL transport.

    To support passive KITL, pass pCfgData->KitlTransport, obtained from the Platform Builder user selections in the boot loader, up to the OAL where it should be used to decide on the argument to KitlInit. See %_WINCEROOT%\Platform\Cepc\Halkitl.c for more information.

    If your SDB has more than one Ethernet port, use one Ethernet port for product Ethernet and another one for debug Ethernet, or EDBG.

    If your SDB only has one Ethernet port, you can implement one of the following:

    • Implement a KITL-based debug Ethernet driver in your boot loader and use the native Ethernet port for debug and download functionality. Then, add VMINI support above the debug Ethernet driver to implement Ethernet sharing. This allows both product and debug Ethernet on the same Ethernet connection. See %_WINCEROOT%\Public\Common\Oak\Drivers\EthDbg\VBridge\Readme.txt.
    • Implement a debug Ethernet driver for downloading and then switch to serial debug from the IDE. This implies that you have implemented the serial debug interface in your boot loader.
