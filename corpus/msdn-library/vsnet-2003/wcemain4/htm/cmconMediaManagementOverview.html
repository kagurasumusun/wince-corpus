Media Manager

Linear flash memory is organized into erase blocks that are too large to efficiently store most files. To compensate for this, PSM includes a Media Manager that can efficiently store multiple files in these erase blocks. The media manager also supports modifying blocks. It does this by logically dividing a large block into smaller allocation units, and then keeping track of what files are stored in which allocation units.

This topic contains information on the architecture and operations relevant to the Media Manager.

Allocation Units

An allocation unit is a logical subdivision of a block. These units contain the minimum amount of memory PSM can use to store a file. When an application creates and writes data into a file, PSM uses allocation units to store the data. PSM uses other areas of the file partition to create and maintain tables and data structures to keep track of the contents and status of all allocation units.

All allocation units in the file partition are the same size, and that size is one of the parameters the OEM can specify. Allocation units should be just big enough to store the typical file in a system. If the system were a web appliance, and if the typical file were a cookie or a favorite with a size of approximately 100 bytes, the size of the allocation units should be 256 bytes, which is the smallest size PSM supports.

Allocation units incur both processing and storage overhead, so selecting a small size divides the file partition up into more units. The control structures needed to keep track of all those units will be bigger, and the performance of the file system slower. Therefore, storing a 6 KB file in twenty-four 256-byte allocation units is less efficient than storing it in one 8192 byte unit. For example, if the device is an MP3 player, and the typical file size is 100 KB, the allocation units should be set to 8192 bytes, which is the largest supported size.

Deleting a File

When an application deletes a file, PSM looks through the control structures to find all allocation units that are being used to store the file. It cannot erase those units, because they reside in blocks that most likely will have allocation units from other files. Instead, it sets a flag in the control structure that tells PSM not to use that allocation unit for any other data.

Modifying a File

When an application modifies a file, parts of the old version are deleted and new sections written. As was the case with a deleted file, the deleted allocation units are flagged, and non-flagged ones are used to store the modified sections.

Reclaim

Over time, as files are deleted and modified, blocks fill up with flagged allocation units. When a block is reclaimed, all allocation units that have valid data are copied into a spare block, the block is erased, and the control structures are updated to note the new location of the data.

If an application tries to write a file, and PSM cannot find enough non-flagged allocation units to store the file, PSM reclaims enough blocks to create enough non-flagged allocation units to store the file. At some point, the only unused space in the file partition contains flagged allocation units. When an application tries to write a file, PSM will have to reclaim the space to store it. Reclaiming a block can take over a second, and it is not unlikely that multiple blocks would need to be reclaimed.

There is no reason to wait until space is needed before a reclaim operation begins. The need for a reclaim begins when a file is deleted or modified; that is when allocation units are flagged. Whenever PSM flags an allocation unit, it decides if that block should be reclaimed. The criteria for that decision are set in the format parameters.

Wear Leveling

Flash blocks can only be erased a limited number of times, typically 100,000 program and erase cycles per block. A typical file partition has many blocks, and it is possible that some of the blocks could be erased more often than others. The erased blocks approach the limited number of times they can be erased sooner than the rest of the blocks.

PSM includes a wear-leveling algorithm that keeps track of how often each block has been erased and avoids erasing blocks that have been heavily erased.
