Priority Inversion

Windows CE supports priority inversion, which refers to a situation in which the use of a mutex, critical section, or semaphore resource by a lower-priority thread delays the execution of a higher-priority thread, when both are contending for the same resources. To correct this situation and free the higher-priority thread, Windows CE allows the lower-priority thread to inherit the more critical thread's priority and run at the higher priority until it releases its use of the resource. Because an unbounded amount of time is needed to relinquish the inverted thread and it is out of the control of the kernel, the OEM loses control of the scheduling process. To guarantee real-time performance, OEMs should ensure that a priority inversion condition does not occur.

For example, suppose a Windows CE application contains threads 1, 2, and 3. Thread 1 is high priority and is ready to be scheduled, thread 2 has medium priority, and thread 3, a low-priority thread, executes code in a critical section. Thread 1 begins waiting for a shared resource from thread 3. Thread 2 receives all the processor time, because thread 1 is waiting for shared resources from thread 3. Thread 3 does not leave the critical section, because it does not have the highest priority and will not be scheduled. To resolve the threading issue, Windows CE guarantees the handling of priority inversion to a depth of one level. Therefore, when thread 1 is blocked as it waits for thread 3 to complete, Windows CE boosts only the priority of thread 3. However, if thread 3 is blocked and waiting for thread 4 to release an object, Windows CE does not boost the priority of thread 3.
