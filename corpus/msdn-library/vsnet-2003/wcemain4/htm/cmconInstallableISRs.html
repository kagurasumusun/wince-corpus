Installable ISRs

An installable interrupt service routine (ISR) is an ISR that can be installed and allowed to hook an interrupt after the kernel is built. Traditionally, if an interrupt had to be hooked to service some event, the code had to be built into the kernel when it was originally built. If a new device was inserted into a PCI bus for example, the code to handle the interrupt request (IRQ) would need to already be in the kernel; otherwise, the IRQ could not be hooked. OEMs could have planned for some expansion and built an OEM adaptation layer (OAL) that accommodated various devices in a flexible way. However, if an unknown device was inserted into the board support package (BSP), there would be a high likelihood that you would not be able to access it.

An OEM only needs to plan what IRQ will be exposed to an ISR that is not built into the kernel. When an ISR is installed, there are two required steps:

  1. The driver DLL is basically the same as any driver DLL that creates an interrupt service thread (IST) and waits for it to be triggered. To install the ISR DLL, call the LoadIntChainHandler function, which will load the ISR DLL into the kernel's address space and initialize it. This function also forces the kernel to create a list of installed ISRs that want to handle a particular interrupt.
    Note   The installable ISR DLL must either be in the FILES section with no fixups or in the MODULES section with the kernel flag, K, set for kernel-style fixups.
  2. The ISR DLL is a stripped down DLL that can be loaded by the kernel and used to service an IRQ. Like a traditional ISR, an installed ISR returns a SYSINTR_* value that triggers a waiting IST in the driver DLL.

Once both steps have been completed, it is up to the OEM to forward any IRQs to the installed ISRs. The OEM is still the first call that the kernel makes if an OEM has hooked an IRQ by calling HookInterrupt. The OEM can handle any IRQs they want in the traditional ISRs that are built into the kernel. The OEM must still plan if it wants an IRQ to be handled by an installed ISR. Any IRQ that the OEM enables to be handled by an installed ISQ will be triggered by a call to NKCallIntChain. When the kernel is called and passed an interrupt value from the OEM, it looks for all the installed ISRs that have registered for the same value. Then, based on a first in, first out (FIFO) ordering, it goes through the list until the first ISR in the list returns a value other than SYSINTR_CHAIN. Once a non-SYSINTR_CHAIN value is returned, the kernel will stop calling any additional installed ISRs and return this value to the caller of NKCallIntChain. If the entire list is processed and ISR does not handle the IRQ, the NKCallIntChain function will return SYSINTR_CHAIN. If the return value from NKCallIntChain is not SYSINTR_CHAIN, the OEM should disable the interrupt and return the SYSINTR_* value to the kernel. If the value returned is SYSINTR_CHAIN, the OEM should return SYSINTR_NOP to the kernel and leave the interrupt enabled.

The generic installable ISR sample code is located in %_WINCEROOT%\Public\Common\Oak\Drivers\GIISR. The generic installable ISR needs to export the following functions:

  • ISRHandler
  • CreateInstance
  • IOControl

The following I/O control codes are specific to the driver:

  • IOCTL_GIISR_INFO
  • IOCTL_GIISR_PORTVALUE
