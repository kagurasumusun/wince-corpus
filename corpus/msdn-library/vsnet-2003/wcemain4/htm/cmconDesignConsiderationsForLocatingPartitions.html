Design Considerations for Locating Partitions

The Intel Persistent Storage Manager (PSM) gives a designer complete control over the size of the array and partitions; however, there are a few tradeoffs with combining both the code and file partitions in a single component or bank.

Most flash memories can only do one thing at a time, so a typical device cannot be read while it is erasing a block or programming a location. Because it cannot be read, instructions cannot be fetched from the component while any part of it is being modified. This has the following implications for system design:

  • The microprocessor must execute from some other device while the flash is being modified. This can be RAM, a second flash component, or an array. The code stored in the alternate memory will usually be a small driver that simply commands the program or erase operation to begin, and then waits for it to complete.
  • If a single device contains both code and data partitions, the code will be unavailable while the file partition is being modified. PSM must ensure that nothing can happen, like an interrupt, which could cause the system to access the code partition during a program or erase of the file partition.

PSM allows both code and data partitions in a single device. It manages the flash similar to how a real-time operating system (RTOS) manages the microprocessor. With an RTOS, when critical tasks need to execute, the RTOS preempts lower priority tasks in favor of the high priority ones. When the high priority task is finished, the lower priority one resumes.

With PSM, because the code partition is not available for execution when the file partition is being modified, if a high priority task needs to execute from the code partition, PSM will suspend the program or erase operation and let the high priority task run to completion. When the high priority task no longer needs to execute from the code partition, the program or erase operation resumes from where it left off.

Storing Code and Files in the Same Component or Bank

This configuration is lower cost and requires fewer components.

Code-size rarely matches the size of flash components, so if a component is dedicated to storing code, some portion of it will be wasted. If code and files are stored in a single device, whatever is not used by code can store files.

In the single component configuration, PSM disables interrupts while modifying the flash. This is the only way to ensure no task attempts to execute from the code partition. When an interrupt occurs, PSM suspends the program or erase operation and enables interrupts; as soon as interrupts are enabled, the interrupt service routine (ISR) executes. The ISR and any related tasks will execute for as long as they need to, and when PSM regains control, it will disable interrupts and resume programming or erasing.

The net effect of all this is that when PSM is used in single component or bank configuration, the maximum interrupt latency will increase. The size of the increase will depend on how long PSM takes to sense the interrupt and issue the suspend command, and once the suspend command is issued, how long the flash component takes to free up the array for execution. The former depends on the performance of the microprocessor. The latter is the component's suspend latency and is specified in the component's datasheet.

Storing Code and Files in Separate Components or Banks

While more expensive, this configuration has the highest performance. If the code and files are in separate components, no interrupt management is necessary, and there will be no increase in the maximum interrupt latency.
