Introduction

This article provides a brief survey of the various performance and profiling tools available in Microsoft® Windows® CE for Automotive version 3.0 and version 3.5. These tools are primarily the ones provided by Windows CE 3.0 and the Windows CE 3.0 Add-On Pack. The Help documentation provided in Windows CE 3.0 contains topics that describe the features and use of the tools. This article introduces the tools, provides some notes regarding their use, and refers the reader to topics in the Help documentation that provide details on each tool.

Some Building Blocks

The QueryPerformanceCounter and QueryPerformanceFrequency functions are two important building blocks for the performance and profiling tools. A number of the tools that are mentioned in the following paragraphs rely heavily on these two functions.

The QueryPerformanceCounter function retrieves the current value of an OEM-provided high-resolution performance counter, and QueryPerformanceFrequency retrieves the frequency of that counter.

Platform Builder provides a default implementation of these functions. These default implementations can be replaced by OEM implementations. In some cases, the OEM implements the QueryPerformanceCounter function by using GetTickCount. In these cases, a call to the QueryPerformanceCounter function returns the value represented by GetTickCount, and QueryPerformanceFrequency returns 1,000, which means 1,000 ticks per second.

The default implementations of these functions can be replaced by defining a custom, high-resolution timer function based on the target device's CPU. The custom high-resolution timer functions must be implemented in the OEM adaptation layer (OAL) code and then be exposed to the kernel.

To expose high-resolution timer functions to the kernel, the kernel provides the global variable function pointer: pQueryPerformanceCounter and pQueryPerformanceFrequency.

The OEM initializes these pointers in the OEMInit routine. In OEMInit, the OEM would initialize pQueryPerformanceCounter and pQueryPerformanceFrequency to point to equivalent private functions such as OEMQueryPerformanceCounter and OEMQueryPerformanceFrequency. These OAL implementations would retrieve the high-resolution timers.

What Are the Tools?

The performance and profiling tools available in Windows CE for Automotive version 3.0 and version 3.5 can be divided into three classes:

  • System Analysis Tools
  • DDTK Tests
  • Display Performance

System Analysis Tools enable an OEM to display detailed information about their Windows CE target platform on their development workstation.

The Driver Development Test Kit (DDTK) contains several tests that provide OEMs with benchmarking information and insight into the real-time performance of their target device running the Windows CE operating system.

Display Performance is a tool to profile the display driver.

System Analysis Tools

System Analysis Tools enable OEMs to display detailed information about their Windows CE target platform on a development workstation. Kernel Tracker, Remote Performance Monitor, and the Monte Carlo Statistical Profiler make up the system analysis tools and are described in the following paragraphs.

Kernel Tracker

Kernel Tracker is a graphical tool that provides a visual representation of a target Windows CE system on a development workstation. Kernel Tracker enables the user to view thread interactions, internal dependencies, and system state information in a quasi-real-time environment. Kernel Tracker includes the following features:

  • Run-time display of process and thread interactions.
  • Tools for searching for events, threads, and processes.
  • Allows viewing and analyzing of the system log.
  • Graphical representations of 49 discreet events in five different categories.

The Platform Builder Help documentation for Kernel Tracker provides a good description of the tool, along with step–by–step instructions for enabling Kernel Tracker on an OEM's device, and a tutorial. You can find the description in the Help documentation available in the Platform Builder version 3.0 IDE at Platform Builder Library->System Analysis Tools->Kernel Tracker.

Remote Performance Monitor

The Remote Performance Monitor (CEPerfMon) is a graphical tool for measuring the performance of a remote Windows CE system. You can view the behavior of performance objects, such as processors, memory, threads, and processes.

Each performance object gets an associated set of performance counters that provide information about device usage, queue lengths, delays, and information used to measure throughput and internal congestion. CEPerfMon provides charting, alerting, and reporting capabilities that reflect both current activity and ongoing logging. You can open, browse, and chart log files later.

While Kernel Tracker enables an OEM to graphically view relationships between events, the Remote Performance Monitor provides the OEM with the ability to focus on the performance data specific to an object.

The Platform Builder Help documentation provides an excellent help topic on the Remote Performance Monitor that includes a detailed description of the tool, along with step–by–step instructions on enabling remote performance monitoring on the OEM's device, and a tutorial. You can find the topic in the Help documentation available in the Platform Builder version 3.0 IDE at Platform Builder Library->System Analysis Tools->Remote Performance Monitor.

Monte Carlo Statistical Profiler

Windows CE supports three profiling techniques to measure operating system performance on a targeted platform. Monte Carlo is one of the three techniques. The Monte Carlo Statistical Profiler can determine which functions the device is spending the greatest amount of time in.

For details on how to instrument your target device to use this profiling technique, use the Help documentation in the Platform Builder version 3.0 IDE. You can find information on the Monte Carlo Statistical Profiler at Platform Builder Library->Operating System Development->Customizing a Platform->Profiling a Platform.

DDTK tests

The Driver Development Test Kit (DDTK) provides a suite of tests to assist OEMs in testing the port of their drivers to the Windows CE operating system. Several of these tests provide the OEM benchmarking and real-time performance information about their target device while running the Windows CE operating system. These tests are:

  • Interrupt Latency Timing test

    The Interrupt Latency Timing test (I1timing.exe) is used to benchmark the real–time performance of the Windows CE operating system on a custom hardware platform.

  • OSBench test

    The Operating System Benchmark test (OSBench.exe) is used to benchmark the time required for the kernel to perform key operations, such as thread switching and event synchronization.

  • QA Interrupt Latency Timing test

    The QA Interrupt Latency Timing test (Qailtiming.exe) is used to benchmark and verify that the real–time performance of the Windows CE operating system is unaffected by various thread activities, thread creation, and the virtual memory manager.

Note   These test binaries and tools have been verified with the supported CPU and hardware reference platforms of Microsoft Windows CE Platform Builder. Because Microsoft tested each DDTK test on a Maxall build, it is recommended that the OEM use a Maxall build when running each DDTK test.

Display Performance

Platform Builder includes a sample profiling tool to profile the performance of a display driver. The tool is called DispPerf. The display driver writer can use DispPerf to profile the performance of a display driver.

DispPerf builds a table of profiled Raster Operation (ROP) codes. For each ROP code profiled, that table lists the frequency count, elapsed time in microseconds, and average elapsed time in microseconds for ROPs handled by:

  • The default GPE emulation
  • The software emulation library
  • The hardware accelerations

Notes on When to Use the Tools

Kernel Tracker is good for a graphical view of "what happens and when it happens" on the system. That is, it helps OEMs determine what events occur in relation to other events.

For example, let's say that you are an OEM debugging a serial driver for a wireless modem. The modem is a PCMCIA–type device. You experience the following problem: in retail mode, you notice that a few bytes are dropped when the driver reads data from the modem. In debug mode, you notice that the driver drips more bytes. You also notice that the modem runs find on other comparable devices running Windows CE, such as a Pocket PC.

The basic question that you would like answered is, "What is the CPU doing instead of retrieving data from the UART?"

Since you are the OEM, you have access to the OAL for the hardware. So, you would:

  1. Add a user-defined Kernel Tracker message when overflow is detected in the UART.
  2. Add a user-defined Kernel Tracker message around flow control on/off in the driver.
  3. Run your tests on Kernel Tracker-enabled kernel, tracking the user-defined messages as well as interrupts and thread scheduling.
  4. Once that the tests are complete, look through the CeLog using Kernel Tracker for the overflow events.
  5. Look at what immediately precedes these events. You'll probably see one of the following:
    • A higher priority interrupt firing for an extended period.
    • A higher priority thread running (higher than the PCMCIA interrupt thread).
    • A priority inversion or other resource conflict.
Note   Although Kernel Tracker is a great viewer of the data in CeLog, you as an OEM are not limited to Kernel Tracker as your only viewer. You also have the option of creating your own viewer that presents a different slice of the data. Use the CeLog.h for a definition of the composition of the CeLog file.

Let's say that you are concerned about the real–time performance of your system. One of the things that you could do would be to benchmark the interrupt service routine (ISR) and interrupt service thread (IST) latencies—the time for the Windows CE OS to respond to interrupts. To do this, you would use the Interrupt Latency Timing test.

You might also want to verify that the real–time performance is unaffected by various types of system operations. You would use the QA Interrupt Latency Timing test for this type of verification.

Let's say that you wanted to understand the system overhead involved key operations, such as thread switching and event synchronization. And you would like to compare these on your device when running XIP from flash or simply running out of RAM. And maybe you are evaluating multiple processors. OSBench would be a good tool to use to collect the benchmark data.

If you are interested in enhancing the performance of an object under your control, you might want to look at the Remote Performance Monitor. With it, you can focus in on the performance of just that object, and then take measurements as you make modifications to validate that your changes are, in fact, enhancing the performance of that object. Keep in mind that an enhancement to the performance of one object does not necessarily translate into enhanced overall system performance.

If you are attempting to enhance the performance of your display subsystem, you may find the DispPerf tool very helpful. A display driver can have a significant effect on the overall performance of a Windows CE device. Tuning the display driver is an iterative process. You will find:

  • It is more valuable to tune the driver for the applications designed to run on the device than tuning the driver in a vacuum.
  • That tuning is an iterative process of:
    • Running the system with DispPerf
    • Analyzing the results
    • Tweaking the driver
    • Repeat until you have the desired performance

About Windows CE for Automotive

Microsoft Windows CE for Automotive is an operating system built on Windows CE technology to make possible new categories of in-car computers that are capable of safely providing drivers and passengers with hands-free communication, access to personalized information on the Internet, the ability to summon emergency services and roadside assistance, and an array of convenience and entertainment applications. Windows CE for Automotive is an open platform that allows developers to quickly create powerful in-car computing solutions. It offers flexibility and choice of computing platforms, hardware peripherals, and software components, as well as a large community of developers familiar with Windows CE development practices.
