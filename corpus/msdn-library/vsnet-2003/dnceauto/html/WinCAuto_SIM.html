Microsoft Software Installation Manager Overview

You have built an in-car computing device based on Microsoft® Windows® CE for Automotive (WCEfA). You have tested your platform code, all of the drivers, as well as the applications that you will be shipping with it. No memory leaks are present. Applications start up and shut down in an orderly fashion and run efficiently.

What about software or data from third parties? Do you want to allow third-party software or data to be installed on your device? If so, can you insure that anything that is allowed also runs efficiently?

Have you considered remote upgrades? What if you need to ship a patch or want to provide an enhancement to a preinstalled application? How can that enhancement be installed once the devices are out of your control?

Microsoft Software Install Manager (SIM), a component of WCEfA, allows you to control what can be installed on your device platform. You can define your platform as being open, closed, or restricted to new installations, and SIM will enforce these designations.

Anything can be installed on an open platform, as long as the applications are compiled for the appropriate processor. At the other extreme, no third-party software can be installed on a closed platform. Only certified applications can be installed on a restricted platform. Regardless of the openness of the platform, you, —the OEM— can always provide updates to the files and data that were originally shipped.

General Development Process

Begin by developing the platform components such as the Hardware Abstraction Layer (HAL), boot loader, and so on. At this time, device drivers can be developed too, possibly in parallel with the platform. Application development starts later.

By this stage in the development process, you have selected the drivers, applications, and data shipping with your product, versus drivers, applications, and data that will be third-party aftermarket additions. Everything that ships as part of your product is included with the ROM image. You should build this image, test it, and eventually manufacture and install the ROM image on your devices.

Once the platform is stable, export to an SDK with the Export-To-SDK function in Platform Builder. Third-party developers will develop applications from this SDK and continue to develop applications from the SDK after the product ships. Once hardware is available, third parties should test the hardware. Any third-party aftermarket applications and drivers should be installed after the device is produced, either by the dealer or directly by the customer.

Software Installation Manager (SIM) Installation

You can set the SIM level of a platform to be open, closed, or restricted to the installation of third-party software. Anything can be installed on an open platform, as long as the applications are compiled for the appropriate processor. At the other extreme, no third-party software can be installed on a closed platform. Only certified applications can be installed on a restricted platform.

Controlling Elements Installed on a Platform

Windows CE for Automotive (WCEfA) installation files use a .cei file extension. The .cei extension is associated with the APCLoad application and should be included in your ROM image.

APCLoad compares various attributes of the device with fields from the .cei file to determine whether the installation can proceed. APCLoad verifies that the platform type and version numbers in the .cei file are consistent with the platform and platform software. APCLoad compares the device SIM level against the .cei file certification key, and either allows the installation to proceed or prohibits it based on the outcome of this comparison.

With open platforms, the installation proceeds regardless of the key. If the platform is closed, the installation does not proceed. If the platform is restricted, APCLoad verifies that the requested file is certified with a valid key before permitting the file installation to proceed. Tampering with a certified .cei file invalidates the certification key, causing APCLoad to refuse to install a file that has been modified.

Certifying Applications or Data

Using the CE Install Builder (CEIBuild) tool, applications, data, speech templates, and so on, are bundled together into an installable file with a .cei extension. A generic CEIBuild tool should be included with your SDK. This generic CEIBuild tool produces .cei files without a certification key. Third-party developers should use .cei files without certification keys to test their product installation process.

Note   Development platforms for independent software vendors (ISVs) must be open, if you want them to successfully test the installation of their product.

If your platform is restricted, then a separate organization will need to validate the applications or data that third parties run on your platform. This validation organization will need a special copy of CEIBuild that adds a certification key to a .cei file.

More on application certification is described below in Certifying an Application.

Updating ROM Components

You may need to change ROM components after your device ships, either to fix a problem, or to provide enhanced functionality. For this purpose, the OEM is given a CEIBuild that adds a master key to a .cei file. CEI files stamped with this master key can be installed on an open, closed, or a restricted platform. Therefore, they can be used to place a file in RAM that supercedes a ROM file with the same name, serving to upgrade the ROM component.

Creating an Open Platform

Finalize OEM and platform names, and modify the following #define directives in platform\inc\autopc.h according to the comments in the file:

  • OEM_NAME_STR (for example: X Corp).
  • OEM_PLATNAME_STR (for example: Fun Car PC).
  • OEM_PLATFORM_STR (for example: X Corp. Fun Car PC version 1.0).
  • OEM_VERSION_NUM_STR (for example: 1.00.0000).

Note that once initially set, OEM and platform names should not be changed.

Modify the following IOCTL in platform\kernel\hal\cfwapc.c:

  • IOCTL_HAL_VALID_SIM_KEY

    Replace the implementation as you see fit. This is the function called when installing or invoking (through Autorun) a file containing an OEM certificate. It is called with an 8-byte fingerprint that you need to validate. If the file being installed was certified with your master key, then 8 bytes will be the same as the 8 bytes of your master key.

Send Microsoft your modified version of autopc.h and an 8-byte sequence for the OEM certificate. Microsoft will return a copy of CEIBuild that generates the master-key certificate for your platform. You will also receive a copy of Certgen.exe that generates the same master-key certificates.

Creating a Closed Platform

Finalize OEM and platform names, and modify the following #define statements in platform\inc\autopc.h according to the comments in the file:

  • OEM_NAME_STR (for example: X Corp).
  • OEM_PLATNAME_STR (for example: Fun Car PC).
  • OEM_VERSION_STR (for example: X Corp. Fun Car PC version 1.0).
  • OEM_VERSION_NUM_STR (for example: 1.00.0000).

Note that once initially set, OEM and platform names should not be changed.

Modify the following IOCTL in platform\kernel\hal\cfwapc.c:

  • IOCTL_HAL_GET_APC_SIM_LEVEL:

    Replace APC_SIM_INSTALL_ANY with APC_SIM_INSTALL_OEM.

    Replace APC_SIM_INVOKE_ANY with APC_SIM_INVOKE_OEM.

  • IOCTL_HAL_VALID_SIM_KEY:

    Replace the implementation as you see fit. This is the function called when installing or invoking (through Autorun) a file containing an OEM certificate. It is called with an 8-byte fingerprint that you need to validate. If the file being installed was certified with your master key, then these 8 bytes will be the same as the 8 bytes of your master key.

Send Microsoft your modified version of autopc.h and an 8-byte sequence for the OEM certificate. Microsoft will return a copy of CEIBuild that generates the master-key certificate for your platform. You will also receive a copy of Certgen.exe that generates the same master-key certificates.

Modify the following IOCTLs in platform\kernel\hal\cfwapc.c:

Remember to inform Microsoft of who will be validating applications for your platform. This could be your own company, or a third-party validation entity. Microsoft will create a program to stamp installation packages with a key that the installer recognizes as valid. This stamping function will be provided to the party that is doing your validation.

Certifying an Application

Before testing begins, the validation testing organization obtains the .cei file from the independent software vendor (ISV) and also obtains restricted production hardware from the OEM. If the submitted application fails, the application and data is rejected. Otherwise, ensure that the platform variables within the .cei file are set appropriately for this platform, then use CEIBuild to stamp the .cei file with a certification key. Send this certified .cei file back to the ISV.

Developer Requirements

Application developers require an SDK created specifically for your device platform. Use the Export-To-SDK function in Platform Builder to create the SDK. Always include the SDKConnect utility in your SDK, so application developers can connect to the device for downloading and testing purposes. Also include the generic CEIBuild tool in the SDK, not the version that stamps your master key, so third parties can package their product into a .cei file and test the installation process.

Third-party software developers should receive the SDK from the OEM, along with development hardware. Ideally, the image on the hardware should be open, not restricted or closed. Develop your application, drivers, and data, download to the device with SDKConnect or CESH, then debug. When everything is operating normally, use CEIBuild to assemble your product. Before testing the installation process, confirm that the correct platform information is included in your .cei file.

Once your application is completed, send the .cei file to the organization that is performing validation or certification for the OEM. They would validate it, then either reject it or return a .cei file that has been stamped with a certification key. You would then reproduce this .cei file on CD-ROM or a compact flash card and distribute.

Testing an Application

Here are some suggestions on what you might want to have your validation provider test. Note that this list is not exclusive.

  • Memory leaks.
  • Thread priorities.
  • CPU efficiency.
  • Does the application survive power cycles?
  • Are properties in the .cei file, such as platform name, platform version, and so on, set correctly for the device?
  • Does the application call certain kernel functions? For example, to increase its priority.
  • Scan the application for viral infection.
  • Does the application work well when other applications are present?

Microsoft Windows CE for Automotive Overview

Microsoft Windows CE for Automotive (WCEfA) operating system is built on Windows CE technology and enables development of automobile computer applications capable of providing drivers and passengers with a variety of options including:

  • Hands-free communication.
  • Access to personalized information on the Internet.
  • The ability to summon emergency services and roadside assistance.
  • Entertainment applications.

WCEfA is an open platform where developers create powerful automobile computing solutions. WCEfA offers flexibility and choice of computing platforms, hardware peripherals and software components, as well as a large community of developers familiar with Windows CE development practices.
