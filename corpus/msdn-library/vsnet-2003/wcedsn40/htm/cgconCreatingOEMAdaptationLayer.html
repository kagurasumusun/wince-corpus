Creating an OEM Adaptation Layer

An OEM adaptation layer (OAL) is a layer of code that logically resides between the Microsoft® Windows® CE .NET kernel and the hardware of your target device. Physically, the OAL is linked with the kernel libraries to create the kernel executable file. The OAL facilitates communication between your operating system (OS) and your target device and includes code to handle interrupts, timers, power management, bus abstraction, generic I/O control codes (IOCTLs), and so on.

Creating the OAL is one of the more complex tasks in the process of getting a Windows CE .NET–based operating system (OS) to run on a new hardware platform. In general, the easiest way to create an OAL is to copy the OAL implementation from a working platform, and then modify it to suit the specific requirements of your platform. If you must create the new OAL from the beginning, the task can be greatly simplified by approaching the development process in stages. Each stage adds a little more functionality than the previous one and provides a convenient separation point where new features can be fixed and validated before proceeding to the next step.

The following table shows the recommended steps for creating a new OAL.

Step Description
1. Preparing the BSP Files for Building the Kernel In this step, you put the necessary directories and files in place to build the OAL and the kernel image. Also, Config.bib is created or modified during this step to allocate requisite resources to the kernel.
2. Creating a Base OAL In this step, you initialize your platform at startup, enable the serial port for debugging, initialize communication settings, and establish a system tick. The goal of this stage is to provide basic system initialization code that will support further debugging and to ensure that basic initialization is complete and consistent with the target device requirements.
3. Enhancing OAL Functionality In this step, you enhance the interrupt service routines (ISRs), manage the clock and timers, configure alternate debugging options like Ethernet, enable power management, and provide platform information for applications. The goal of this stage is to implement the remainder of the platform support functions and ensure that a full OS boot is possible.
4. Completing an OAL In this step, you implement any additional features. For example, you can log processes, create a CEDDK, define extension memory, erase the object store, support high-resolution timers, and configure the registry.
