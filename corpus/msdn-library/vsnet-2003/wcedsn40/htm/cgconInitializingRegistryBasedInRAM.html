Persisting Data with the RAM-Based Registry

The RAM-based registry supports two different save-and-restore mechanisms. OEMs can use these mechanisms to persist registry data when the RAM, which contains the object store, is not being powered. In addition, the mechanisms can also be used to provide last-known-good protection against invalid data configurations.

The first mechanism is based on the APIs RegCopyFile and RegRestoreFile. RegCopyFile saves the entire registry to a file, and RegRestoreFile sets up the registry to be replaced with the data in the given file on the next boot. To persist the registry when a device is powered off, an OEM would first use RegCopyFile to save the data to a persistent file. Then on the next cold boot, the OEM would call RegRestoreFile to prepare the registry to be replaced with data in the file, and do a warm reboot to do the registry replacement. This manner of registry persistence is easy to implement, but since it requires a dual-boot to restore the registry after a device was powered off, it is relatively slow. The RegCopyFile and RegRestoreFile mechanism is better suited to providing last-known-good backup to protect against errors than it is to providing registry persistence.

The second mechanism gives the OEM responsibility for persisting the data. An OEM can implement the two functions WriteRegistryToOEM and ReadRegistryFromOEM in their OAL. These functions, if implemented, are called by the registry code to save and restore the data. When an application calls RegFlushKey, the OS makes a series of calls to WriteRegistryToOEM to pass the entire registry to the OEM, who stores the data on any persistent media. Then when the system is booting, it makes another series of calls to ReadRegistryFromOEM to receive the data from wherever the OEM stored it. The difficulty in using this mechanism is that file system calls such as CreateFile, ReadFile, and WriteFile, cannot be used to read the data from storage during ReadRegistryFromOEM. While they can be used during WriteRegistryToOEM, the block and file system drivers needed to read from external media are not started until after the registry is initialized. Therefore, implementing ReadRegistryFromOEM is difficult; code to read from the persistent media must be added to the OAL. But this mechanism has the benefit of requiring only a single boot to restore the registry, as opposed to the dual-boot required by the RegCopyFile and RegRestoreFile mechanism.

These pairs of APIs, RegCopyFile and RegRestoreFile, and WriteRegistryToOEM and ReadRegistryFromOEM, cannot be intermixed. The file produced by RegCopyFile is not the same as that produced by WriteRegistryToOEM.

To make use of either save-and-restore mechanism, you must understand how Windows CE initializes the RAM-based registry. The following list shows the process of initializing the RAM-based registry:

  1. The system initializes the kernel.
  2. The kernel launches Filesys.exe.
  3. Filesys.exe initializes the RAM file system.
  4. Filesys.exe initializes the database subsystem.
  5. Filesys.exe initializes the registry by checking for a registry in RAM. If one is found, go to step 7.
  6. If Filesys.exe does not find a registry in step 5, it restores the registry from ROM. Filesys.exe loads \Windows\Default.fdf, which was created using Makeimg.exe.
  7. Filesys.exe checks for the ReadRegistryFromOEM OEM adaptation layer (OAL) function. If Filesys.exe does not find ReadRegistryFromOEM, it keeps the registry from ROM, as described in step 6.
  8. Filesys.exe tries to restore \Windows\Restore.fdf, which is created with the RegCopyFile function. If Filesys.exe cannot restore \Windows\Restore.fdf, it keeps the registry from ROM, as described in step 6.
  9. Filesys.exe checks one more time for ReadRegistryFromOEM. If Filesys.exe does not find ReadRegistryFromOEM, it keeps the registry from ROM as described in step 6.

You cannot access files that would exist on a PC Card or any other device that is serviced by a device driver that is managed by Device.exe because Device.exe has not been loaded. Also, you cannot allocate memory to pass to the system because the registry saving and loading functionality is implemented in the OAL.

To initialize a RAM-based registry

  1. Expose the ReadRegistryFromOEM and WriteRegistryToOEM functions in your OAL after Filesys.exe initializes the RAM file system.
  2. If an OAL is not available, use the RegCopyFile and RegRestoreFile functions to initialize a registry from RAM.

    RegCopyFile saves the registry and RegRestoreFile restores the registry.

  3. After RegRestoreFile succeeds, reset your device for the new registry settings to take effect.

You can create a boot sequence so that the user is unaware that a reset has occurred by configuring the HKEY_LOCAL_MACHINE\Init registry key. In this registry key, you can restore the registry and reboot without launching Gwes.exe. Then, you can do a full startup. By preventing Gwes.exe from launching, the display does not become active and therefore the user is unaware that any reset has occurred.

Using RegCopyFile and RegRestoreFile to initialize a registry from RAM requires enough of the system to be running to restore the registry. The portions of the system that must be running depend on where your registry file resides. For example, if your registry file resides on a PC Card, Device.exe must be running before the registry can be restored. Otherwise, your system cannot access the registry file on the PC Card.
