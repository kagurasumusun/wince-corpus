Device Management Service Design

To function efficiently, the basic service is designed as a pull model rather than a push-based model. The device periodically polls a server for new application offerings or packages. A scheduler on the device controls the frequency and the conditions of the polling.

The following process describes how the device management service works:

  1. The user, or administrator, configures the device to connect to a server for management and application updates.
  2. Periodically, a service on the device connects to the server using HTTPS to check if there are any updates.
  3. The device posts to the server its current hardware configuration (hardware inventory), and the list of packages (software inventory) that it detects as available to it.
  4. If there are any updates since the last poll, the server responds with an XML document that informs the device about what packages it should either add or remove from its list.
  5. The device updates its internal list of packages and determines if it needs to request any packages from the server.
  6. If packages are required, the device requests the specific packages from the server.
  7. The device downloads instructions for the package, in the format of an XML document, and a download event is scheduled. The download event could be triggered immediately or could wait for specific connection conditions, such as when the device is docked. The scheduling criteria, including priority, time schedule, bandwidth restrictions are part of the download instructions.
  8. The device downloads the files specified in the XML document at the scheduled time. It then runs the command line specified in the XML, which is typically a command line to the shell to execute the .CAB file. The Windows CE installer (WCELoad) then installs the application or operating system (OS) update.
  9. When the task is completed, the device reports the status of the task to the URL specified by the server.
