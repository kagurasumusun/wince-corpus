Recovering Memory through Application Hibernation

Windows CE uses the WM_HIBERNATE message as its primary mechanism for asking applications to free memory. When freeing memory becomes necessary, the operating system posts the message to one or more applications, beginning with the application that has been inactive the longest. The OS requests memory from the active application last and does not send WM_HIBERNATE messages to invisible windows. Your device platform may specify other ways to monitor and handle memory allocation. For more information, see the OEM-supplied SDK for your target device.

As the amount of available memory decreases, the OS increasingly posts WM_HIBERNATE messages to its applications. If the system reaches a situation where a call to VirtualAlloc is about to fail, it will attempt to free pages by shrinking stacks. To minimize the risk of a stack fault, which causes an application to fail, the system shrinks stacks in first-in and first-out order. If the system cannot free any stack pages, VirtualAlloc fails and the function is returned to the application as a failed function call.

An application must take the following step when it receives a WM_HIBERNATE message:

  • Free any large blocks of memory that were allocated by VirtualAlloc.
  • Free as many Graphics, Windowing, and Event Subsystem (GWES) objects as possible.
  • Save the state of the heap in order to restore it later, and then free the entire heap.

In the low and critical memory states, the amount of memory an application can allocate is limited. In these states, if a request for virtual memory is larger than the allowable limit, it will be refused even if there is memory available to satisfy the request. Remember that not only virtual memory allocations are limited; allocations on the heap and stack will be rejected if those allocations require virtual memory allocations above the allowable limits, which are set by the OEM.
