Kato Design Benefits

The following list shows Kato design benefits:

  • The Kato client is built as a .dll file that can be linked into any application.
  • The Kato logging interface is implemented primarily as a C++ class. This allows applications to easily pass around logging objects. A flat C interface is also exposed. This is useful if you wish to dynamically load Kato.dll at runtime, or if you prefer using C.
  • More than one Kato object can be created within any application. Each Kato object maintains a unique stream to the server. This may be useful if you have multiple threads performing independent tasks. Each thread can log independently of the other thread, without having their logs interlaced in the output.
  • The Kato interface supports ANSI and UNICODE logging, on both Windows 95/98 and Windows NT.
  • The client side of Kato is small and fixed in size. It does not dynamically change if logging output systems are added or deleted because they reside on the server side.
  • The client/server architecture of Kato allows applications and the Kato server to run on separate machines running different operating systems. The Kato client currently runs on Windows 95/98, Windows NT, and Windows CE. The Kato server runs on Windows 95/98 and Windows NT. The Kato server runs more efficiently on Windows NT because it makes use of the faster I/O completion ports of Windows NT.
  • Kato supports hierarchical logging. Applications may begin and end levels at any time. This is useful for group logging or to show a log that is a subset of the current log.
  • Kato supports log filtering. Each log line is associated with a verbosity value. This value determines the importance of a given log line. The Kato server allows the user to set a filter for each output system. This filtering mechanism allows users to mask out a log of less importance.
  • Kato supports verbosity tracking. The Kato client keeps tallies for each of the different verbosity values. These values can later be queried to find out how many lines of a given verbosity have been logged. This is useful for generating log summaries and pass/fail information.
  • Several callback hooks have been placed in the Kato client. Applications can request to have the log of all Kato objects within the given process routed to a callback. This can be useful for test harness type applications that request to perform a task with the log.
  • Third-party add-on systems can easily be written and plugged into the server. These systems can monitor data or store data to any device they choose. You need not be concerned with multi-thread issues and synchronization for your system because the server internally prohibits reentrance to the systems.
  • All user interface (UI) and configuration has been isolated to the server side.
  • The server UI is object-oriented through a drag and drop interface. Logging streams from Kato clients have a many-to-many association with output systems. More than one output system may be attached to a single Kato client log stream. Likewise, multiple Kato client log streams may be attached to a single output system.
