Running the Test

The following command line shows the syntax for using Tux.exe to run the test, where test_case is the specific test case or range of test cases to run.

tux –o –d pserial –x test_case

The following command line shows the syntax for using Tux.exe to run the entire test.

tux –o –d pserial

After each test case finishes, a status report is displayed indicating whether it passed, failed, skipped, or aborted. After all of the specified test cases have finished, a summary of results is displayed.

Before running this test, you should confirm all serial cable connections; there must be a cable for debug output and a cable for serial test communications. You should verify that the RAS server is not running on the Windows NT workstation.

Pserial.dll is a client/server program. This means that one machine runs as the client or slave (-s parameter) and the other machine runs as the server or master (-m parameter). Each time you run this test, you must have one master and one slave. Slave-to-slave and master-to-master tests are not supported.

It is important to run the test in both configurations on Windows CE. Tests that run successfully when the Windows CE machine is the master may fail when it is the slave.

When running Pserial.dll using the -x parameter to select individual test cases, it is important to always include test cases 10 and 11. Test case 10 verifies the serial connection and the ability of the two devices to synchronize. Test case 11 determines what features the two serial ports share and is required when running the other test cases.

In addition to the standard Tux parameters for selecting tests to run, Pserial.dll supports its own set of parameters that are passed by using the Tux –c parameter.

Test Case 20

The TestXonXoffIdle test case is designed to do the following:

  • Test software flow control

    If software flow control is not working when the receiver sends an XOFF, the sender will rapidly transmit the rest of its data and the test will fail. End synchronization will not occur.

  • Determine if the serial driver on the tested platform is going to sleep while waiting for data.
  • Determine how well the driver releases resources while sleeping

    This is tested by measuring 3 IdleThreadDelta time values. The value of IdleThreadDelta determines how much time has passed between operating system calls to a low priority function. The larger the IdleThreadDelta value, the more work the OS is performing and the less time the low priority function has to operate.

    The following 3 IdleThreadDelta values are measured:

    • Sleep
    • Baseline communications with software flow control disabled
    • Communications with software flow control enabled

    For testing purposes, we are interested in the difference in time between communications with software flow control enabled and communications with software flow control disabled. The former should not be significantly longer than the latter. This test case fails if communication with software flow control enabled is more than 25 percent longer than communication with software flow control disabled.

Test Cases 20 and 21

The following information applies to test cases 20 and 21:

  • The slave machine receives the data and sends the flow control.
  • The master machine transmits data and responds to the flow control.
