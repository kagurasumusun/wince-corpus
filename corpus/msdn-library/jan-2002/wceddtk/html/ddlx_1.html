Running the Test

The following command line shows the syntax for running a test using Ddlx.dll

tux –d ddlx –c “-d test_dll –i device_index -c parameters”

The parameters outside of the quotation marks (-d ddlx –c) are parameters for Tux. They instruct Tux to load Ddlx.dll into the Tux process space and then pass the entire string enclosed in quotation marks to Ddlx.dll.

In the parameter list for Ddlx.dll, which is enclosed in quotation marks, a space is not required between a command line option and its argument. However, each command line option must be specified separately from the other command line options. For example, the following command line is not acceptable.

tux -d ddlx -c “-dtest.dll-i2”

The following table shows the parameters for DDLX.

Parameter Description
-d test_dll Instructs DDLX which file to register. If this option is not specified, DDLX will attempt to load Generic.dll.
-i device_index Specifies the device index for the driver (-i2 for gen2:, for example). If this option is not specified, DDLX will use 1.
-c parameters Specifies additional test_dll parameters to pass on to the device driver being tested.

The following command line shows the syntax for a sample test.

tux –o –d ddlx –c “-d test.dll –i 2 –c 1 2 3”

The device driver being tested will receive the following string as a command line: “1 2 3”.

If you do not need to specify the device index or any additional command line parameters, you can leave out the quotation marks and the –d parameter. The syntax for this is shown in the following command line.

tux –o –d ddlx –c test.dll

The general layout for writing test procedures is the same for Tux/Ddlx as it is for Tux alone. These test procedures consist of creating the function table, processing ShellProc commands, processing TestProc commands, and so on. However, there are two differences between a normal Tux test procedure and a Tux/Ddlx test procedure that are in the context of the make file:

  • Ddlxioct.lib must be linked with your test procedure as a source library, not as a target library.
  • Your .def file needs to include all required device driver entry points.

Since your test program will be running as a device driver, it must accept DeviceIoControl commands. However, Ddlxioct.lib will handle the processing of these commands by receiving them and passing them along to your test procedure as standard Tux messages. No additional coding is required in your test procedure.

Note that Ddlxioct.lib does not implement any of these procedures; it only returns a passing value to satisfy device.exe.

Ddlxioct.lib also exposes a function to control debugger output. DDLXDebuggerControl accepts a DWORD containing flags set for debugger output, and returns a DWORD indicating the previous state of the debugger’s output. In order to use this function, you must include Ddlx.h. For more information, see Ddlx.h.

The following code example shows a typical .mak file:

TARGETNAME=ddlxtest
TARGETTYPE=DYNLINK
TARGETLIBS=\
   $(_COMMONSDKROOT)\lib\$(_CPUINDPATH)\coredll.lib \
   $(_PROJECTOAKROOT)\lib\$(_CPUINDPATH)\kato.lib
DLLENTRY=DllMain
INCLUDES=\
   $(_PUBLICROOT)\common\oak\inc
SOURCES=shelproc.cpp \
   testproc.cpp \
   globals.cpp
SOURCELIBS=\
   $(_PROJECTOAKROOT)\lib\$(_CPUINDPATH)\ddlxioct.lib

The following code example shows a typical .def file.

EXPORTS
   ShellProc
   gen_Init
   gen_Deinit
   gen_Open
   gen_Close
   gen_Read
   gen_Write
   gen_Seek
   gen_IOControl
   gen_PowerUp
   gen_PowerDown
